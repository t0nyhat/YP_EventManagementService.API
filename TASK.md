# Задание

В этом спринте вы сделаете первый шаг к созданию сервиса для управления мероприятиями на ASP.NET Core Web API.

В первой практической работе нужно реализовать базовый REST API для создания, просмотра, обновления и удаления мероприятий.

По итогам у вас получится каркас приложения с минимальным набором функциональности, который можно будет расширять дальше.

## Результат выполнения работы

В результате выполнения проектной работы вы:

- реализуете базовый REST API с CRUD-операциями;
- научитесь выносить бизнес-логику в сервисы и подключать их через DI;
- закрепите работу с HTTP-статусами и валидацией входных данных;
- получите стартовый каркас приложения Web API, который будете расширять в следующих спринтах.

## Требования и функциональность

- Проект на C#, .NET 8 или выше (рекомендуем актуальную версию), ASP.NET Core Web API.
- Код приложения хранится в публичном GitHub-репозитории.
- Проект собирается и запускается стандартными средствами (`dotnet build`, `dotnet run`).
- Структура проекта простая и понятная, с базовым разделением кода по назначению. Не требуется применять какие-либо архитектурные подходы, достаточно аккуратной организации.
- У сервиса есть доступный Swagger, чтобы быстро тестировать API.
- Данные о событиях хранятся в памяти приложения (например, `List<Event>`).
- Бизнес-логика и работа с данными вынесены в отдельные классы-сервисы (например, `EventService`).
- Сервисы реализуют интерфейсы (например, `IEventService`).
- Сервисы зарегистрированы в DI-контейнере с нужным жизненным циклом в зависимости от реализации.
- Реализованы эндпоинты REST API с использованием контроллеров или minimal API.
- Эндпоинты не содержат бизнес-логику, только вызовы сервиса.

## Как работать над заданием

### Этап 1. Подготовка проекта

- Изучите требования к проекту.
- Создайте новый публичный репозиторий на GitHub.
- Клонируйте репозиторий себе на компьютер.
- Создайте ветку с названием `sprint-1` из ветки `main` и переключитесь на неё.
- Создайте проект ASP.NET Core Web API и сделайте стартовый коммит. Все работы по этой проектной работе ведите в ветке `sprint-1`.

### Этап 2. Реализация доменной логики

- Реализуйте модель `Event`.
- Состав полей:
	- `Id` (`Guid` или `int`, обязательное);
	- `Title` (`string`, обязательное);
	- `Description` (`string`, опциональное);
	- `StartAt` (`DateTime`, обязательное);
	- `EndAt` (`DateTime`, обязательное).
- Создайте интерфейс сервиса `IEventService`.
- Реализуйте сервис для работы с событиями.
- Зарегистрируйте зависимости (в DI-контейнере).

### Этап 3. Реализация API

- Реализуйте эндпоинты REST API:
	- `GET /events` — получить список всех событий;
	- `GET /events/{id}` — получить событие по `id`; если не найдено — вернуть корректный HTTP-ответ (например, `404`);
	- `POST /events` — создать событие, возвращать корректный HTTP-ответ (например, `201`);
	- `PUT /events/{id}` — обновить событие целиком; если не найдено — вернуть корректный HTTP-ответ (например, `404`);
	- `DELETE /events/{id}` — удалить событие; если не найдено — вернуть корректный HTTP-ответ (например, `404`).
- Добавьте валидацию входных данных:
	- обязательность полей `Title`, `StartAt`, `EndAt`;
	- `EndAt` позже `StartAt`.

### Этап 4. Проверка и оформление

- Добавьте Swagger.
- Протестируйте работу API через Swagger.
- Добавьте `README.md` с инструкцией для запуска и краткой документацией API.
- Убедитесь, что проект запускается и все методы API работают.
- Сделайте финальный commit и push всех изменений в ветку `sprint-1` на GitHub.

### Этап 5. Сдача работы

- Создайте pull request из ветки `sprint-1` в ветку `main` вашего репозитория.
- Скопируйте ссылку на созданный pull request.
- В тренажёре в уроке с проектом вставьте ссылку на pull request в поле для ссылки и нажмите «Отправить».
- Ревьюер проверит ваш код по чек-листу. Он оставит комментарии в pull request, если потребуются правки.
- После того как правки по всем комментариям будут внесены, ревьюер одобрит pull request.
- Выполните слияние изменений в ветку `main`.

## Чек-лист проверки для ревью

### Работа возвращается без проверки, если

- Нет ссылки на репозиторий или репозиторий приватный/недоступен.
- Проект не собирается (`dotnet build` выдаёт ошибку).
- Проект не запускается (`dotnet run` выдаёт ошибку).
- Нет доступного Swagger.
- Нет `README.md`.

### Критические требования (без этого работа не принимается)

- Реализована сущность `Event` с обязательными полями.
- Реализован `GET /events`.
- Реализован `GET /events/{id}`.
- Реализован `POST /events`.
- Реализован `PUT /events/{id}`.
- Реализован `DELETE /events/{id}`.
- Данные хранятся в памяти приложения.
- Бизнес-логика вынесена в сервис.
- Сервис подключён через DI.
- Реализована валидация обязательных полей.
- Эндпоинты возвращают корректные HTTP-статусы.
- Swagger корректно отображает все эндпоинты.
- Проект запускается по инструкции из `README`.

### Хорошие практики (необязательно для зачёта)

- использовать DTO для запроса/ответа и маппинг вместо общей модели для всего;
- централизовать ошибки (единый формат ошибки, problem details).

### Отлично (всё выполнено на высоком уровне)

- аккуратное разделение слоёв: эндпоинты тонкие, вся логика в сервисе;
- чёткие HTTP-ответы и предсказуемое поведение (включая ошибки/валидацию);
- чистая структура проекта и именование;
- история коммитов отражает этапы работы (не один коммит на всё).
