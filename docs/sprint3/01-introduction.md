# Введение и обзор спринта 3

## Назначение третьего спринта

Если sprint 1 строил базовый CRUD для `Event`, а sprint 2 добавлял ошибки, фильтрацию, пагинацию и тесты, то sprint 3 делает проект заметно ближе к реальному серверному приложению.

Появляются три новых инженерных направления:

1. **Вторая сущность, связанная с первой**  
   Теперь API работает не только с событиями, но и с бронированиями этих событий.

2. **Паттерн “быстрый ответ + отложенная обработка”**  
   Запрос на создание брони завершается сразу с `202 Accepted`, а фактическая обработка происходит позже.

3. **Фоновая обработка вне HTTP-запроса**  
   Проект начинает использовать `BackgroundService`, то есть в приложении появляется поток работы, который живёт отдельно от контроллеров.

## Что изменилось относительно sprint 2

Во втором спринте проект оставался в рамках классического request/response API:

- клиент отправляет запрос;
- контроллер вызывает сервис;
- сервис сразу возвращает результат;
- middleware при необходимости оформляет ошибку.

В третьем спринте жизненный цикл стал сложнее:

1. Клиент создаёт бронь через `POST /api/events/{id}/book`.
2. API возвращает `202 Accepted`, а не конечное подтверждение.
3. В ответе приходит `Location` со ссылкой на ресурс брони.
4. Отдельный worker позже переводит бронь из `Pending` в `Confirmed`.
5. Клиент может опрашивать `GET /api/bookings/{id}` и видеть смену статуса.

Это уже полноценный пример асинхронного процесса внутри Web API.

## Что именно добавлено в sprint 3

### 1. Новая доменная модель

Появились:

- `Booking`
- `BookingStatus`

Теперь проект работает уже с двумя связанными сущностями:

- `Event` — первичный ресурс
- `Booking` — зависимый ресурс, который ссылается на событие через `EventId`

### 2. Отдельное хранилище бронирований

Для бронирований введён `IBookingStore` / `InMemoryBookingStore`.

Это важное изменение, потому что состояние бронирований должно быть доступно не только API-сервису, но и фоновому обработчику.

### 3. Новый сервис прикладной логики

Появился `IBookingService` / `BookingService`.

Он отвечает за:

- проверку существования события;
- создание pending-брони;
- чтение брони по `Id`.

### 4. Новые endpoint-ы

Проект получил два новых HTTP-маршрута:

- `POST /api/events/{id}/book`
- `GET /api/bookings/{id}`

Они отделены от event CRUD, но логически остаются привязаны к существующей архитектуре контроллеров и DTO.

### 5. Фоновый обработчик

Добавлен `BookingProcessingBackgroundService`, который:

- опрашивает store;
- находит `Pending`-брони;
- ждёт искусственную задержку;
- переводит бронь в `Confirmed`;
- заполняет `ProcessedAt`.

### 6. Расширенный тестовый слой

Теперь в проекте есть:

- unit-тесты на `BookingService`;
- тесты доменной модели `Booking`;
- тесты `InMemoryBookingStore`;
- изолированный тест на `BookingProcessingBackgroundService`;
- integration-тест полного сценария `create -> pending -> confirmed`.

## Чему учит этот спринт

### 1. Разнице между `201 Created` и `202 Accepted`

Это один из ключевых учебных моментов sprint 3.

- `201 Created` означает: ресурс уже полностью создан и операция завершена.
- `202 Accepted` означает: запрос принят, но окончательная обработка произойдёт позже.

В проекте это видно очень наглядно:

- событие создаётся синхронно;
- бронирование принимается сразу, но подтверждается позже.

### 2. Работе с `BackgroundService`

`BackgroundService` — это не “ещё один сервис”, а отдельный тип жизненного цикла внутри ASP.NET Core приложения.

Он позволяет:

- запускать фоновые циклы;
- использовать `CancellationToken`;
- безопасно завершать работу при остановке приложения;
- не завязывать долгую обработку на время HTTP-запроса.

### 3. Разделению общего состояния между API и worker'ом

В sprint 2 состояние событий жило внутри `EventService`.

В sprint 3 для бронирований это уже не лучший вариант, потому что:

- API создаёт брони;
- worker обрабатывает брони;
- обоим нужен доступ к одним и тем же данным.

Отсюда появляется отдельный store как явная точка хранения.

### 4. Тестированию асинхронного поведения

Теперь тесты проверяют не только результат метода, но и изменение состояния во времени:

- сначала бронь `Pending`;
- позже она становится `Confirmed`;
- поле `ProcessedAt` заполняется не при создании, а при обработке.

Это важный шаг от “статического CRUD” к более реальным серверным сценариям.

## Ключевые результаты спринта

По факту реализации проект теперь умеет:

- создавать бронь для существующего события;
- возвращать `202 Accepted` и `Location`;
- хранить бронирования в памяти приложения;
- отдавать текущее состояние брони через отдельный endpoint;
- обрабатывать брони в фоне через `BackgroundService`;
- подтверждать поведение через unit- и integration-тесты.

## Что особенно полезно изучить в этом спринте

### 1. Почему `BookingService` зависит от `IEventService`

Это простой, но важный пример повторного использования существующей бизнес-логики:

- сервис бронирований не лезет напрямую в список событий;
- проверка существования события централизована;
- кейс “удалённое событие” тоже автоматически работает корректно.

### 2. Почему `InMemoryBookingStore` возвращает snapshot, а не живые ссылки

Это хороший учебный пример того, как даже in-memory код можно писать аккуратно с точки зрения потокобезопасности и разделения ответственности.

### 3. Почему worker переводит бронь всегда в `Confirmed`

Несмотря на наличие `Rejected` в enum, текущая реализация детерминирована.

Это сделано осознанно:

- так проще демонстрировать сценарий;
- так проще писать стабильные тесты;
- логика выбора статуса может быть добавлена позже без изменения базовой архитектуры.

### 4. Почему sprint 3 важен методологически

Этот спринт хорош не столько размером кода, сколько набором технологий, которые он связывает в одном учебном примере:

- DTO
- DI
- singleton shared state
- async API contract
- background worker
- unit-tests
- integration-tests

Именно поэтому его полезно читать не только как “ещё одну фичу”, а как связанный инженерный сценарий.
