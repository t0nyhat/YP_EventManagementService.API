Задание

В этом спринте вы продолжите развивать сервис для управления мероприятиями:
добавите новую сущность Booking;
реализуете паттерн «быстрый ответ + отложенная обработка»;
настроите фоновую обработку заявок.
Вы реализуете эндпоинт создания брони, который мгновенно возвращает 202 Accepted со ссылкой на ресурс. Обработку выполняет фоновый сервис с искусственной задержкой (имитация вызова внешней системы).
Также вы добавите отдельный эндпоинт для получения текущего статуса брони и напишете юнит-тесты для новой функциональности.
В результате выполнения проектной работы вы:

добавите в модель сервиса вторую сущность, связанную с существующей;
реализуете паттерн «отложенная обработка + быстрый ответ» в API;
научитесь работать с BackgroundService для фоновой обработки задач;
закрепите возврат HTTP-статуса 202 Accepted с заголовком Location;
напишете юнит-тесты для новой бизнес-логики и фонового сервиса;
получите сервис с двумя связанными сущностями и асинхронной обработкой.
Требования и функциональность

Проект использует C#, .NET 8 и выше, ASP.NET Core Web API.
Код приложения хранится в том же публичном GitHub-репозитории.
Проект собирается и запускается стандартными средствами (dotnet build, dotnet run).
Тесты запускаются командой dotnet test и успешно проходят.
Swagger доступен и корректно отображает новые эндпоинты.
Данные о бронированиях хранятся в памяти приложения (аналогично событиям).
Бизнес-логика работы с бронированиями вынесена в отдельный сервис (например, BookingService).
Сервис реализует интерфейс (например, IBookingService) и зарегистрирован в DI-контейнере.
Фоновая обработка заявок реализована через BackgroundService.
Эндпоинты не содержат бизнес-логику, только вызовы сервиса.
Как работать над заданием

Этап 1. Подготовка к работе

Убедитесь, что проектная работа второго спринта успешно завершена и принята.
Переключитесь на ветку main вашего репозитория и выполните git pull для синхронизации.
Создайте новую ветку sprint-3 из ветки main и переключитесь на неё.
Все работы по этой проектной работе ведите в ветке sprint-3.
Этап 2. Реализация сущности Booking

Реализуйте модель Booking.
Состав полей:
Id (Guid, обязательное) — уникальный идентификатор брони;
EventId (Guid, обязательное) — идентификатор события, к которому относится бронь;
Status (BookingStatus, обязательное) — текущий статус брони;
CreatedAt (DateTime, обязательное) — дата и время создания брони;
ProcessedAt (DateTime?, опциональное) — дата и время обработки брони.
Реализуйте перечисление BookingStatus со значениями: 
Pending — бронь создана, ожидает обработки;
Confirmed — бронь подтверждена;
Rejected — бронь отклонена.
Реализуйте хранилище для бронирований в памяти (аналогично хранилищу событий).
Убедитесь, что при создании бронь получает статус Pending, уникальный Id и текущую дату в CreatedAt.
Этап 3. Реализация сервиса бронирований

Создайте интерфейс IBookingService с методами: 
CreateBookingAsync(Guid eventId) — создание брони для указанного события;
GetBookingByIdAsync(Guid bookingId) — получение брони по идентификатору.
Реализуйте сервис BookingService.
Зарегистрируйте IBookingService и BookingService в DI-контейнере.
Этап 4. Реализация эндпоинтов

Реализуйте эндпоинт POST /events/{id}/book: 
вызывает BookingService.CreateBookingAsync;
возвращает 202 Accepted;
в теле ответа возвращает информацию о созданной брони (включая Id, EventId, Status);
в заголовке Location возвращает ссылку на ресурс брони (например, /bookings/{bookingId});
если событие не найдено — возвращает 404.
Реализуйте эндпоинт GET /bookings/{id}: 
возвращает текущее состояние брони по её идентификатору;
возвращает 200 OK с информацией о брони;
если бронь не найдена — возвращает 404.
Убедитесь, что Swagger корректно отображает новые эндпоинты.
Этап 5. Фоновая обработка бронирований

Реализуйте фоновый сервис на базе BackgroundService: 
сервис периодически опрашивает хранилище на наличие бронирований в статусе Pending;
для каждой необработанной брони выполняется искусственная задержка (например, Task.Delay на 2 секунды), имитирующая обращение к внешней системе;
после задержки бронь переводится в статус Confirmed (в следующих спринтах вы добавите логику выбора статуса);
после смены статуса заполняется поле ProcessedAt;
обновлённая бронь сохраняется в хранилище.
Зарегистрируйте фоновый сервис в DI-контейнере через AddHostedService.
Убедитесь, что после создания брони через POST /events/{id}/book и ожидания нескольких секунд повторный запрос GET /bookings/{id} показывает изменённый статус.
Этап 6. Написание юнит-тестов

Добавьте тесты для сервиса BookingService.
Успешные сценарии:
создание брони для существующего события — возвращается BookingInfo со статусом Pending;
создание нескольких броней для одного события — все создаются с уникальными Id;
получение брони по Id — возвращается корректная информация;
получение брони отражает изменение статуса (после Confirm/Reject).
Неуспешные сценарии:
создание брони для несуществующего события;
создание брони для удалённого события;
получение брони по несуществующему Id.
Убедитесь, что все тесты проходят успешно (dotnet test).
Этап 7. Проверка и оформление

Протестируйте сценарий целиком через Swagger: 
создайте событие через POST /events;
создайте бронь через POST /events/{id}/book — убедитесь, что получили 202 Accepted и Location;
сразу запросите GET /bookings/{id} — статус должен быть Pending;
подождите несколько секунд и повторите запрос — статус должен измениться на Confirmed или Rejected.
Обновите README.md: 
добавьте описание новых эндпоинтов (POST /events/{id}/book, GET /bookings/{id});
опишите модель Booking и статусы;
опишите логику фоновой обработки;
добавьте пример сценария использования.
Убедитесь, что: 
проект собирается и запускается без ошибок;
все тесты проходят успешно.
Сделайте финальный commit и push всех изменений в ветку sprint-3 на GitHub.
