# Архитектурные решения sprint 3

В третьем спринте ключевые архитектурные изменения затронули четыре области:

- общий доступ к состоянию бронирований;
- новый сервис прикладной логики;
- асинхронный HTTP-контракт с `202 Accepted`;
- фоновую обработку вне request pipeline.

Ниже разбирается не только “что сделано”, но и “почему именно так”.

## Общая структура после sprint 3

После добавления бронирований проект можно описать как упрощённую многослойную архитектуру:

1. **Presentation Layer**  
   `Controllers/EventsController.cs`  
   `Controllers/EventBookingsController.cs`  
   `Controllers/BookingsController.cs`  
   Здесь живут HTTP-маршруты, коды успешных ответов, привязка DTO и маппинг в response-модели.

2. **Application / Business Layer**  
   `Services/IEventService.cs`, `Services/EventService.cs`  
   `Services/IBookingService.cs`, `Services/BookingService.cs`  
   Здесь находятся бизнес-операции: работа с событиями, создание брони, чтение брони, бизнес-валидация и доменные ошибки.

3. **Shared State / Store Layer**  
   `Stores/IBookingStore.cs`, `Stores/InMemoryBookingStore.cs`  
   Здесь находится общее in-memory состояние бронирований, доступное и сервису API, и worker'у.

4. **Background Processing Layer**  
   `BackgroundServices/BookingProcessingBackgroundService.cs`  
   Здесь живёт асинхронный цикл, который периодически обрабатывает pending-брони.

5. **Infrastructure Layer**  
   `Program.cs`  
   `Middleware/ExceptionHandlingMiddleware.cs`  
   Здесь настроены DI, middleware, Swagger, `ProblemDetails`, `InvalidModelStateResponseFactory`, lifetimes сервисов и hosted service.

6. **Contracts Layer**  
   `Dtos/*.cs`  
   `Mappings/*.cs`  
   DTO и маппинги отделяют HTTP-контракт от доменной модели.

7. **Tests Layer**  
   `EventManagementService.API.Tests/*`  
   Здесь закреплено поведение событий, бронирований, store, worker'а и HTTP-контракта.

## Почему для бронирований введён отдельный store

### Проблема наивного варианта

Если бы список бронирований хранился прямо внутри `BookingService`, сразу возникли бы два вопроса:

1. Как фоновый worker получит доступ к тем же данным?
2. Где должна жить потокобезопасность при одновременном чтении и записи?

В итоге `BookingService` начал бы совмещать:

- бизнес-логику;
- техническое хранение данных;
- инфраструктурные детали многопоточного доступа.

### Выбранный вариант

В проекте выделены:

- `IBookingStore`
- `InMemoryBookingStore`

Это лучше, потому что:

1. Появляется одно место хранения бронирований.
2. `BookingService` остаётся сервисом прикладной логики, а не контейнером списка.
3. Worker работает со store напрямую, не раздувая `BookingService` техническими методами.
4. Поведение store можно тестировать отдельно.

## Почему `BookingService` зависит от `IEventService`

Файл: `Services/BookingService.cs`

На уровне архитектуры можно было бы выбрать несколько вариантов:

- прямой доступ к `EventService` internals;
- второй отдельный store событий;
- зависимость от `IEventService`.

Выбран третий вариант.

### Почему это хорошее решение

1. Уже существующая логика поиска события не дублируется.
2. Проверка существования события остаётся централизованной.
3. Кейс “создание брони для удалённого события” автоматически корректен, потому что `BookingService` использует текущий реальный источник истины.
4. Новый сервис строится поверх уже работающего контракта sprint 2, а не ломает его.

## Почему методы `IBookingService` асинхронные

Файл: `Services/IBookingService.cs`

Хотя данные сейчас хранятся в памяти, методы имеют сигнатуры:

- `Task<Booking> CreateBookingAsync(Guid eventId)`
- `Task<Booking> GetBookingByIdAsync(Guid bookingId)`

Это сделано не ради “лишней async-магии”, а по двум понятным причинам:

1. Так требует задание.
2. Публичный контракт уже выглядит готовым к будущему развитию, если вместо in-memory появится внешнее хранилище.

Такой подход полезен в учебном проекте, потому что показывает разницу между текущей реализацией и внешним контрактом сервиса.

## Почему worker вынесен в `BackgroundService`

Файл: `BackgroundServices/BookingProcessingBackgroundService.cs`

Вариант “обрабатывать бронь внутри POST endpoint-а” был бы проще только внешне, но он ломал бы главный смысл sprint 3.

### Если делать обработку прямо в запросе

- клиент ждал бы весь `Task.Delay`;
- ответ перестал бы быть “быстрым”;
- `202 Accepted` потерял бы смысл;
- не было бы отдельной фоновой модели работы приложения.

### Почему `BackgroundService` лучше

`BackgroundService` позволяет:

- запускать отдельный цикл вне контроллеров;
- обрабатывать брони независимо от конкретного запроса;
- использовать `CancellationToken`;
- корректно завершать работу при остановке приложения;
- логировать ошибки без падения всего API.

Это и есть главный технологический смысл sprint 3.

## Почему worker обрабатывает брони последовательно

Внутри `BookingProcessingBackgroundService` pending-брони берутся snapshot'ом и затем обрабатываются по одной.

Это сделано осознанно:

- последовательная обработка проще;
- она предсказуемее для учебного проекта;
- не требует дополнительного статуса `Processing`;
- уменьшает риск случайных гонок.

Для production-системы такой worker мог бы быть сложнее, но для sprint 3 именно эта модель даёт наилучшее соотношение понятности и полезности.

## Почему store и сервисы зарегистрированы как singleton

Файл: `Program.cs`

В DI используются:

```csharp
builder.Services.AddSingleton<IEventService, EventService>();
builder.Services.AddSingleton<IBookingStore, InMemoryBookingStore>();
builder.Services.AddSingleton<IBookingService, BookingService>();
builder.Services.AddHostedService<BookingProcessingBackgroundService>();
```

### Почему это правильно

1. Проект целиком in-memory.
2. Данные должны быть общими между запросами.
3. Worker и API обязаны видеть одно и то же состояние бронирований.

Если бы `IBookingStore` был, например, `Scoped`, фоновый worker и контроллеры могли бы работать с разными экземплярами хранилища, что полностью сломало бы сценарий.

## Почему события и бронирования хранятся несимметрично

Это важный архитектурный нюанс текущего проекта.

Сейчас:

- события по-прежнему хранятся внутри `EventService`;
- бронирования вынесены в отдельный `InMemoryBookingStore`.

На первый взгляд это выглядит асимметрично, но решение разумное.

### Почему такая асимметрия допустима

Для `Event` пока есть только один непосредственный потребитель состояния — `EventService`.

Для `Booking` потребителей уже два:

- `BookingService`
- `BookingProcessingBackgroundService`

То есть отдельный store добавлен не “ради красивой симметрии”, а потому что у бронирований появился другой жизненный цикл.

## Почему endpoint-ы разделены по сущностям

В проекте используется два контроллера для бронирований:

- `EventBookingsController` для `POST /api/events/{id}/book`
- `BookingsController` для `GET /api/bookings/{id}`

Это хороший компромисс:

- создание брони остаётся в контексте события;
- чтение брони живёт как чтение самостоятельного ресурса;
- event CRUD не смешивается с booking retrieval.

Такое разделение хорошо соответствует хорошим практикам из задания.

## Почему маршруты сделаны явными и lowercase

В sprint 3 маршруты заданы явно:

- `api/events`
- `api/bookings`

Это лучше token-based варианта вроде `api/[controller]`, потому что:

- маршруты не зависят от имени класса;
- Swagger выглядит предсказуемо;
- `Location` в ответах получается консистентным;
- API-контракт становится явным, а не косвенно вычисляемым.

## Почему ошибки не потребовали отдельного нового слоя

Sprint 3 добавляет новые ресурсы, но не меняет принцип обработки ошибок.

Проект по-прежнему использует:

- `InvalidModelStateResponseFactory` для model validation;
- `ExceptionHandlingMiddleware` для `NotFoundException`, `BusinessValidationException` и остальных ошибок.

Это хороший архитектурный знак: новая функциональность встроилась в уже готовую инфраструктуру, а не потребовала нового отдельного механизма.

## Что особенно полезно изучить в архитектуре sprint 3

### 1. Появление второго жизненного цикла

Теперь в приложении есть:

- request lifecycle
- background lifecycle

И это меняет требования к хранению данных и сервисам сильнее, чем кажется по размеру кода.

### 2. Shared state как отдельный слой

`InMemoryBookingStore` — это самый наглядный инженерный шаг sprint 3.

Он показывает, что даже в учебном проекте полезно явно отделять:

- бизнес-операции;
- общий mutable state;
- фоновые технические процессы.

### 3. Эволюция проекта без большого рефакторинга

Sprint 3 не ломает sprint 2, а аккуратно его расширяет:

- события остаются как есть;
- добавляется параллельный контур бронирований;
- общий pipeline ошибок и Swagger сохраняется;
- тестовый проект расширяется, но не переписывается с нуля.

Это и есть хороший пример постепенной эволюции архитектуры.
