# Эндпоинты и фоновая обработка

Этот раздел объясняет, как в sprint 3 реализован полный пользовательский сценарий:

1. создать событие;
2. создать бронь для события;
3. сразу получить `202 Accepted`;
4. прочитать бронь как `Pending`;
5. дождаться фоновой обработки;
6. прочитать бронь повторно как `Confirmed`.

Здесь же разбирается, почему именно такой сценарий был выбран и как он отражён в коде.

## Общая идея sprint 3

Главное технологическое отличие sprint 3 от предыдущих спринтов:

HTTP-запрос больше не обязан дождаться окончания всей операции.

Вместо этого проект использует паттерн:

**быстрый ответ + отложенная обработка**

### Что это значит на практике

- клиент быстро получает подтверждение, что запрос принят;
- сервер продолжает работу уже после завершения запроса;
- состояние ресурса меняется асинхронно;
- клиент отслеживает результат через отдельный endpoint.

## `POST /api/events/{id}/book`

Файл: `Controllers/EventBookingsController.cs`

Маршрут:

```http
POST /api/events/{id}/book
```

### Что делает контроллер

Контроллер получает:

- route-параметр `{id}`;
- привязывает его к `CreateBookingRequest`;
- вызывает `bookingService.CreateBookingAsync(request.EventId)`;
- возвращает `AcceptedAtRoute(...)`.

Ключевой фрагмент:

```csharp
var booking = await bookingService.CreateBookingAsync(request.EventId);
return AcceptedAtRoute(
    BookingsController.GetBookingByIdRouteName,
    new { id = booking.Id },
    booking.ToResponse());
```

## Почему используется `AcceptedAtRoute`

Это одно из самых полезных мест для изучения в sprint 3.

`AcceptedAtRoute(...)` даёт сразу три эффекта:

1. HTTP-статус `202 Accepted`
2. `Location` с адресом ресурса
3. тело ответа с `BookingResponse`

То есть контроллер одновременно сообщает:

- запрос принят;
- вот ресурс, который можно опрашивать дальше;
- вот текущие данные по нему.

## Что возвращает `POST /api/events/{id}/book`

### Статус

`202 Accepted`

### Заголовок

`Location: /api/bookings/{bookingId}`

### Тело ответа

```json
{
  "id": "5b178c2f-247d-4e6f-bf64-c40aeb9f95ef",
  "eventId": "0c6bbd2b-4f64-4fb9-8d73-dcd7f6f36611",
  "status": "Pending",
  "createdAt": "2026-04-03T12:00:00Z",
  "processedAt": null
}
```

### Почему сразу не `201 Created`

Потому что бронирование уже создано как ресурс, но не завершило весь жизненный цикл обработки.

На момент ответа:

- бронь существует;
- у неё есть `Id`;
- она уже доступна по `GET /api/bookings/{id}`;
- но итог обработки ещё не завершён.

Именно поэтому `202 Accepted` здесь семантически корректнее, чем `201 Created`.

## Ошибки при создании брони

Если событие не найдено, `BookingService` получает `NotFoundException` через `IEventService`.

Дальше ошибка уходит в уже существующий `ExceptionHandlingMiddleware`, и клиент получает:

- `404 Not Found`
- `application/problem+json`

Это полезно отметить: sprint 3 не вводит специальный отдельный способ обработки ошибок для бронирований, а встраивается в существующую инфраструктуру sprint 2.

## `GET /api/bookings/{id}`

Файл: `Controllers/BookingsController.cs`

Маршрут:

```http
GET /api/bookings/{id}
```

### Что делает контроллер

- принимает `id`;
- вызывает `bookingService.GetBookingByIdAsync(id)`;
- маппит модель в `BookingResponse`;
- возвращает `200 OK`.

Это очень тонкий controller action, что соответствует общей архитектуре проекта.

## Что показывает `GET /api/bookings/{id}`

Этот endpoint нужен для чтения текущего состояния ресурса.

Он может вернуть:

- `Pending`
- `Confirmed`
- `Rejected`

В текущей реализации sprint 3 practically будут встречаться:

- `Pending`
- `Confirmed`

### Почему это важно

GET endpoint здесь не “второстепенный”, а часть основного async-сценария:

- без него клиент не узнает, чем завершилась отложенная обработка;
- именно он делает `Location` в `POST` полезным.

## Почему creation и reading split по разным контроллерам

В проекте создание брони находится в:

- `EventBookingsController`

А чтение брони — в:

- `BookingsController`

Это хороший учебный компромисс:

- создание логически относится к событию;
- чтение относится к ресурсу брони;
- маршруты остаются простыми и предсказуемыми.

## `BookingProcessingBackgroundService`

Файл: `BackgroundServices/BookingProcessingBackgroundService.cs`

Это главный технический центр sprint 3.

Он наследуется от `BackgroundService` и внутри `ExecuteAsync(...)` запускает бесконечный цикл, который:

1. читает pending-идентификаторы из store;
2. обрабатывает каждую pending-бронь;
3. ждёт между итерациями цикла.

## Алгоритм фоновой обработки

### Шаг 1. Снять snapshot pending-броней

```csharp
var pendingIds = _bookingStore.GetPendingIds();
```

Worker не получает живые объекты, а работает через идентификаторы.

Это снижает связанность и упрощает безопасное обновление статуса.

### Шаг 2. Для каждой pending-брони выполнить обработку

Для каждой записи вызывается:

```csharp
await ProcessBookingAsync(bookingId, stoppingToken);
```

### Шаг 3. Выполнить искусственную задержку

Внутри `ProcessBookingAsync(...)` используется:

```csharp
await Task.Delay(ProcessingDelay, cancellationToken);
```

Сейчас `ProcessingDelay = 2 секунды`.

Это имитирует обращение к внешней системе и даёт нужный учебный эффект:

- бронь не подтверждается мгновенно;
- клиент реально может наблюдать переход `Pending -> Confirmed`.

### Шаг 4. Перевести бронь в `Confirmed`

После задержки worker вызывает:

```csharp
_bookingStore.TrySetStatus(bookingId, BookingStatus.Confirmed, DateTime.UtcNow);
```

То есть:

- итоговый статус в sprint 3 всегда `Confirmed`;
- `ProcessedAt` ставится в момент завершения обработки.

## Почему worker не обрабатывает запись напрямую

Worker не делает что-то вроде:

```csharp
booking.Status = BookingStatus.Confirmed;
```

Вместо этого он работает через store и доменную модель.

Это даёт:

1. одно место контроля за изменением состояния;
2. защиту от повторной обработки;
3. более чистое разделение ответственности.

## Что делает `TrySetStatus`

Если бронь:

- уже обработана;
- отсутствует;

store вернёт `false`.

Worker в таком случае не падает, а просто пишет информационный лог и идёт дальше.

Это важный практический момент: даже в учебном проекте фоновые процессы лучше делать устойчивыми к повторным и “запоздалым” операциям.

## Обработка отмены и ошибок

В `ExecuteAsync(...)` есть два важных защитных механизма.

### 1. `CancellationToken`

Worker использует `stoppingToken`:

- в основном цикле;
- в `Task.Delay`;
- в обработке отмены.

Это позволяет приложению завершаться корректно.

### 2. `try/catch` вокруг обработки каждой брони

Если одна бронь вызовет исключение, worker:

- залогирует ошибку;
- не остановит весь фоновой цикл;
- продолжит работать с остальными заявками.

Это полезный учебный пример устойчивого фонового сервиса.

## Логирование

`BookingProcessingBackgroundService` использует:

`ILogger<BookingProcessingBackgroundService>`

Логи пишутся для:

- запуска worker'а;
- остановки worker'а;
- начала обработки брони;
- успешного перехода в `Confirmed`;
- пропуска уже обработанной брони;
- ошибок при обработке.

### Почему это полезно

В спринте 3 это не просто “хорошая практика ради галочки”.

Логирование реально помогает:

- понять, что worker вообще запущен;
- увидеть факт обработки;
- связывать поведение API и внутренний фоновой цикл.

## Ручной сценарий проверки через Swagger

Чтобы изучить sprint 3 руками, полезно пройти именно такой сценарий:

1. Создать событие через `POST /api/events`.
2. Скопировать `id` созданного события.
3. Выполнить `POST /api/events/{id}/book`.
4. Посмотреть на:
   - `202 Accepted`
   - тело ответа
   - заголовок `Location`
5. Сразу выполнить `GET /api/bookings/{bookingId}`.
6. Убедиться, что статус — `Pending`.
7. Подождать несколько секунд.
8. Повторить `GET /api/bookings/{bookingId}`.
9. Убедиться, что статус стал `Confirmed`, а `processedAt` заполнен.

Это лучший способ увидеть весь смысл sprint 3, не читая код построчно.

## Что особенно важно понять в этом разделе

### 1. Контроллеры не “знают” про delay

HTTP-слой никак не управляет задержкой и не ждёт её завершения.

### 2. `Location` здесь не декоративный

Это реальный адрес ресурса, который нужен клиенту для следующего шага.

### 3. Worker является частью приложения, а не отдельным процессом

Это важно для понимания `AddHostedService`, DI и shared state.

### 4. Sprint 3 — это уже не простой CRUD

Появляется распределение ответственности во времени:

- часть операции происходит “сейчас”;
- часть — “позже”.

Это и есть главный учебный результат третьего спринта.
