# Модель бронирований, store и сервис

Этот раздел разбирает основной прикладной слой sprint 3:

- доменную модель `Booking`;
- enum `BookingStatus`;
- DTO и маппинг;
- `IBookingStore` / `InMemoryBookingStore`;
- `IBookingService` / `BookingService`.

Именно здесь находится большая часть новой предметной логики спринта.

## Модель `Booking`

Файл: `Models/Booking.cs`

`Booking` описывает бронь конкретного события и содержит поля:

- `Id`
- `EventId`
- `Status`
- `CreatedAt`
- `ProcessedAt`

### Почему это отдельная доменная модель

Можно было бы представить бронирование как “просто анонимный объект ответа API”, но в проекте выбрана именно полноценная доменная сущность.

Это полезно, потому что:

- состояние брони меняется во времени;
- у модели есть инварианты;
- у неё есть естественные операции (`CreatePending`, `Confirm`, `Reject`);
- модель удобно тестировать отдельно от HTTP и store.

## Почему поля имеют `private set`

Поля `Booking` не открыты для произвольной записи извне:

```csharp
public Guid Id { get; private set; }
public BookingStatus Status { get; private set; }
```

Это сделано не ради “инкапсуляции ради инкапсуляции”, а чтобы:

- не допустить случайное изменение статуса снаружи;
- централизовать переходы состояния через методы модели;
- избежать ситуации, когда кто-то выставит `ProcessedAt` без изменения статуса или наоборот.

## Фабричный метод `CreatePending`

Создание новой брони выполняется через:

```csharp
Booking.CreatePending(eventId)
```

### Что он гарантирует

1. Генерацию нового `Id`
2. `Status = Pending`
3. `CreatedAt = DateTime.UtcNow`
4. `ProcessedAt = null`
5. Проверку, что `eventId` не пустой

Это один из самых полезных учебных моментов sprint 3: доменное состояние инициализируется не “где попало”, а централизованно.

## Методы `Confirm` и `Reject`

`Booking` содержит два доменных перехода:

- `Confirm(...)`
- `Reject(...)`

Оба метода:

- меняют `Status`;
- выставляют `ProcessedAt`;
- работают только для брони в статусе `Pending`.

Если попытаться повторно обработать уже завершённую бронь, модель бросит `InvalidOperationException`.

Это означает, что правило “обрабатывать можно только pending-брони” закреплено на уровне модели, а не только на уровне store или worker'а.

## Почему в модели есть `Snapshot()`

Файл: `Models/Booking.cs`

В sprint 3 у `Booking` появился внутренний метод:

```csharp
internal Booking Snapshot()
```

Он нужен для `InMemoryBookingStore`.

### Зачем это нужно

Если store будет отдавать наружу ту же самую ссылку на объект, которую он хранит у себя:

- внешний код сможет менять состояние мимо store;
- снимки состояния потеряют смысл;
- поведение worker'а и сервисов станет менее предсказуемым.

`Snapshot()` решает эту проблему, создавая копию текущего состояния.

## Enum `BookingStatus`

Файл: `Models/BookingStatus.cs`

Содержит:

- `Pending`
- `Confirmed`
- `Rejected`

### Почему `Rejected` есть уже сейчас

Текущий worker переводит брони только в `Confirmed`, но `Rejected` всё равно оставлен:

- это прямое требование задания;
- модель не придётся расширять позже;
- тесты уже могут покрывать поведение `Reject`.

Это хороший пример проектирования “на шаг вперёд” без лишнего усложнения текущей логики.

## DTO для бронирований

### `CreateBookingRequest`

Файл: `Dtos/CreateBookingRequest.cs`

Этот DTO необычен тем, что не принимает JSON-тело, а заполняется из route:

```csharp
[FromRoute(Name = "id")]
public Guid EventId { get; set; }
```

### Зачем это полезно

1. Входной контракт операции явно оформлен отдельным типом.
2. Good practice про отдельные request/response DTO закрывается даже для route-only endpoint-а.
3. Код контроллера остаётся единообразным: он получает request model, а не голый набор параметров.

### `BookingResponse`

Файл: `Dtos/BookingResponse.cs`

Этот DTO используется и для:

- ответа `POST /api/events/{id}/book`
- ответа `GET /api/bookings/{id}`

Он содержит:

- `Id`
- `EventId`
- `Status`
- `CreatedAt`
- `ProcessedAt`

### Почему response DTO важен

Даже если структура DTO сейчас близка к самой модели, это всё равно полезное разделение:

- доменная модель не становится публичным HTTP-контрактом;
- API можно менять независимо от внутренних классов;
- в будущем response можно расширять без раскрытия внутренней логики.

## `BookingMappings`

Файл: `Mappings/BookingMappings.cs`

В sprint 3 маппинг брони вынесен отдельно:

```csharp
booking.ToResponse()
```

Это продолжает стиль sprint 2, где маппинг DTO тоже вынесен из контроллера.

### Почему это хорошо

1. Контроллеры не захламляются ручной сборкой response-моделей.
2. Все преобразования находятся в одном месте.
3. Структура API-контрактов читается быстрее.

## Контракт `IBookingStore`

Файл: `Stores/IBookingStore.cs`

Интерфейс store описывает четыре операции:

- `Add`
- `GetById`
- `GetPendingIds`
- `TrySetStatus`

### Почему набор именно такой

Store не дублирует весь возможный CRUD, а даёт только то, что действительно нужно sprint 3:

- API-сервису — создание и чтение;
- worker'у — поиск pending-записей и безопасное обновление статуса.

Это полезный учебный пример интерфейса, который строится от сценариев использования, а не “на всякий случай”.

## `InMemoryBookingStore`

Файл: `Stores/InMemoryBookingStore.cs`

Внутри store используется:

- `Dictionary<Guid, Booking>`
- `lock`

### Почему `Dictionary`, а не `List`

Для бронирований важны:

- быстрое получение по `Id`;
- уникальность `Id`;
- удобство адресного обновления одной записи.

Под такие операции `Dictionary<Guid, Booking>` подходит лучше, чем список.

### Почему есть `lock`

Store используется из разных контекстов:

- из HTTP-запросов;
- из background worker'а.

Поэтому конкурентный доступ реален даже в учебном проекте.

`lock` нужен, чтобы:

- атомарно читать и писать состояние;
- не получать гонки между worker'ом и контроллерами;
- не держать логику потокобезопасности размазанной по всему приложению.

### Почему `Add` не перезаписывает существующую запись

Если `Id` уже существует, store бросает:

`InvalidOperationException`

Это лучше, чем молча заменить старую запись, потому что:

- дубликат `Id` — это ошибка, а не допустимое поведение;
- поведение store становится строгим и предсказуемым;
- такой случай легче заметить на тестах.

### Почему `GetPendingIds()` возвращает только `Id`

Worker получает snapshot pending-идентификаторов, а не сами объекты `Booking`.

Это полезно по нескольким причинам:

1. Worker не держит наружу ссылку на внутреннее состояние store.
2. Позже worker повторно просит обновить запись через `TrySetStatus(...)`, а значит всё изменение проходит через один защищённый API.
3. Меньше риска случайно менять состояние “в обход” store.

### Почему `TrySetStatus` возвращает `bool`

Метод обновляет статус только если бронь всё ещё `Pending`.

Если бронь:

- не найдена;
- уже обработана;

метод возвращает `false`.

Это особенно полезно для worker'а, потому что делает повторную обработку безопасной.

## `IBookingService`

Файл: `Services/IBookingService.cs`

Контракт сервиса минимален:

- `CreateBookingAsync(Guid eventId)`
- `GetBookingByIdAsync(Guid bookingId)`

### Почему этого достаточно

Sprint 3 не требует:

- отмены бронирования;
- удаления бронирования;
- фильтрации списка бронирований;
- ручной смены статуса через API.

Поэтому сервис содержит ровно те операции, которые реально нужны текущему сценарию.

## `BookingService`

Файл: `Services/BookingService.cs`

`BookingService` зависит от:

- `IBookingStore`
- `IEventService`

### Как работает `CreateBookingAsync`

Алгоритм очень компактный, но архитектурно важный:

1. Проверяет существование события через `IEventService.GetEventById(eventId)`.
2. Если события нет, получает `NotFoundException`.
3. Создаёт `Booking.CreatePending(eventId)`.
4. Сохраняет бронь в store.
5. Возвращает сохранённую запись.

### Почему это хорошая композиция

- сервис бронирований не знает, как именно хранятся события;
- сервис бронирований не лезет в internals `EventService`;
- создание брони не дублирует логику проверки ресурса.

### Как работает `GetBookingByIdAsync`

Алгоритм:

1. Берёт бронь из store.
2. Если брони нет, бросает `NotFoundException`.
3. Возвращает результат.

Это соответствует принципу thin application service:

- минимум транспортной логики;
- минимум инфраструктуры;
- ровно один прикладной сценарий на метод.

## Как этот слой связан с тестами

В sprint 3 все ключевые элементы прикладного слоя покрыты отдельно:

- доменная модель `Booking` — собственными unit-тестами;
- `InMemoryBookingStore` — собственными тестами;
- `BookingService` — собственными unit-тестами;
- worker — отдельным изолированным тестом;
- HTTP-контракт — integration-тестом.

Это делает код удобным для изучения: почти каждое важное решение подкреплено отдельным тестовым примером.
