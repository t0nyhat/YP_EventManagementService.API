# Архитектурные решения sprint 2

Во втором спринте ключевые архитектурные изменения затронули три области:

- обработку ошибок;
- чтение коллекции событий;
- тестируемость бизнес-логики.

Ниже разбирается не только “что сделано”, но и “почему сделано именно так”.

## Общая структура после sprint 2

Проект по-прежнему следует упрощённой многослойной архитектуре:

1. **Presentation Layer**  
   `Controllers/EventsController.cs`  
   Здесь живут HTTP-маршруты, привязка DTO, коды успешных ответов и маппинг результата.

2. **Application / Business Layer**  
   `Services/IEventService.cs`, `Services/EventService.cs`  
   Здесь находятся бизнес-правила, поиск, фильтрация, пагинация и операции над сущностью `Event`.

3. **Infrastructure Layer**  
   `Middleware/ExceptionHandlingMiddleware.cs`  
   `Program.cs`  
   Здесь настроены middleware, DI, Swagger, `ProblemDetails`, model validation response factory.

4. **Contracts Layer**  
   `Dtos/*.cs`  
   DTO отделяют HTTP-контракты от доменной модели и позволяют развивать API без раскрытия внутренней структуры.

5. **Tests Layer**  
   `EventManagementService.API.Tests/*`  
   Отдельный проект с unit-тестами, который закрепляет поведение `EventService`.

## Почему обработка ошибок вынесена в middleware

### Проблема “локальной обработки”

Если каждый контроллер сам решает, как возвращать ошибки:

- формат начинает расползаться;
- ошибки описываются по-разному;
- часть ошибок возвращается как `BadRequest(...)`, часть как анонимный объект, часть как `500` без тела;
- дублируется код.

### Почему middleware лучше

`ExceptionHandlingMiddleware` перехватывает все необработанные исключения в одном месте и:

- логирует проблему;
- преобразует исключение в нужный HTTP-статус;
- возвращает `ProblemDetails`.

Это делает поведение API предсказуемым и облегчает расширение.  
Если позже появится `ConflictException` или, например, `UnauthorizedOperationException`, достаточно будет расширить отображение исключений в middleware.

## Почему используются кастомные исключения

В проекте введены:

- `BusinessValidationException`
- `NotFoundException`

Это лучше, чем бросать базовый `Exception`, потому что код сразу выражает смысл проблемы.

### Что это даёт

1. **Явный доменный смысл**  
   `throw new NotFoundException(...)` читается как часть бизнес-логики.

2. **Простое отображение в HTTP**  
   Middleware может надёжно сопоставить тип исключения со статусом.

3. **Удобство тестов**  
   Тесты проверяют именно ожидаемое поведение:
   `Assert.Throws<NotFoundException>(...)`, а не абстрактный `Exception`.

## Почему бизнес-валидация перенесена в сервис

### Слабый вариант

Если правило `EndAt > StartAt` проверяется только в контроллере, то:

- сервис остаётся “тупым”;
- при прямом вызове сервиса правило легко обойти;
- тестировать бизнес-логику сложнее, потому что она размазана по HTTP-слою.

### Выбранный вариант

В проекте правило проверяется в `EventService.ValidateEvent(...)`.

Это правильно, потому что:

- сервис является владельцем бизнес-инвариантов;
- контроллер остаётся транспортным слоем;
- тесты работают напрямую против сервиса, без HTTP.

## Почему фильтрация и пагинация находятся в `EventService`

Задание прямо требует реализовать их в сервисе, но это решение и архитектурно оправдано.

### Причины

1. **Контроллер не должен знать детали выборки**  
   Его задача — принять `GetEventsQuery` и вернуть результат.

2. **Логика должна быть повторно используемой**  
   Если позже тот же сервис будет вызван не из HTTP, а из фоновой задачи или другого слоя, поведение останется тем же.

3. **Сервис легче тестировать**  
   Unit-тесты могут проверять фильтрацию и пагинацию без участия ASP.NET Core.

## Почему используется LINQ

В `EventService.GetEvents(...)` LINQ выбран не только потому, что этого требует задание, но и потому что он естественно описывает pipeline обработки списка:

1. стартуем с набора событий;
2. условно применяем `Where`;
3. задаём упорядочивание;
4. считаем общий размер;
5. применяем `Skip` / `Take`.

Такой код хорошо читается и легко переносится на будущую работу с БД или ORM.

## Почему `EventService` остаётся Singleton

`EventService` хранит состояние в `_events`, а данные должны быть общими для всех запросов.

```csharp
builder.Services.AddSingleton<IEventService, EventService>();
```

Если бы сервис был:

- `Transient` — список пересоздавался бы слишком часто;
- `Scoped` — данные зависели бы от запроса и терялись бы между обращениями.

Для in-memory учебного API `Singleton` — правильный выбор.

## Почему используется `lock`

Так как `EventService` — singleton и хранит изменяемую коллекцию, несколько запросов могут одновременно:

- читать список;
- добавлять события;
- обновлять события;
- удалять события.

`lock (_lock)` нужен, чтобы избежать гонок при доступе к `_events`.

### Почему не `ConcurrentDictionary` или `ConcurrentBag`

Они хорошо работают для отдельных атомарных операций, но хуже выражают сценарии вида:

- найти запись;
- проверить условие;
- изменить запись.

Для учебного проекта простой `lock`:

- понятнее;
- надёжнее;
- легче объясняется.

## Почему перед LINQ создаётся snapshot списка

В `GetEvents(...)` под `lock` берётся копия текущего списка:

```csharp
List<Event> snapshot;
lock (_lock)
{
    snapshot = _events.ToList();
}
```

Дальше вся фильтрация идёт уже по `snapshot`, вне критической секции.

### Это решение полезно потому что:

- уменьшает время удержания `lock`;
- делает поиск более безопасным;
- не блокирует остальные операции дольше, чем нужно.

Это интересный момент: даже в маленьком проекте видно стремление разделять защищённое чтение состояния и последующую обработку.

## Почему выбран `ProblemDetails`

`ProblemDetails` — это стандартный формат описания ошибок в HTTP API.

Преимущества:

- предсказуемая структура;
- понятная интеграция с ASP.NET Core;
- удобно расширять `Extensions`, например `traceId`;
- легче документировать и проверять.

Для учебного проекта это лучший выбор, чем самодельный анонимный JSON.

## Почему дополнительно настроен `InvalidModelStateResponseFactory`

Есть важное различие:

- middleware ловит исключения;
- ошибки `ModelState` могут происходить без исключения, на этапе model binding.

Если не настроить `InvalidModelStateResponseFactory`, то часть ошибок будет возвращаться в одном формате, а часть — в другом.

Настройка в `Program.cs` делает ответы валидации ближе к общему стилю API.

## Почему тестовый проект расположен рядом с основным проектом

Выбран формат:

```text
EventManagementService.API/
├── EventManagementService.API.csproj
├── EventManagementService.API.Tests/
│   └── EventManagementService.API.Tests.csproj
```

Это сделано по практической причине учебного проекта: чтобы команды из корня работали без дополнительных аргументов.

### Важный нюанс

Так как основной `.csproj` расположен в корне репозитория, он по умолчанию мог бы “подхватить” `.cs` файлы тестов как свои. Поэтому в основном проекте используется `DefaultItemExcludes`.

Это хорошая прикладная деталь, показывающая, что структура решения влияет на поведение MSBuild.

## Почему выбран `xUnit`

`xUnit` хорошо подходит для учебного и реального .NET-проекта:

- простой синтаксис;
- удобные `Fact`;
- естественный стиль AAA;
- де-факто один из самых распространённых вариантов в экосистеме .NET.

Дополнительные assertion-библиотеки вроде `FluentAssertions` здесь не обязательны: текущие тесты достаточно читаемы и без них.

## Осознанно неиспользованные инструменты

Во sprint 2 проект не усложняется следующими слоями:

- `Repository`
- `Entity Framework`
- `AutoMapper`
- `FluentValidation`
- `MediatR`

### Почему это нормально

Проект учебный, а цель спринта — понять:

- middleware;
- LINQ-фильтрацию;
- пагинацию;
- unit-тесты.

Дополнительные абстракции здесь скорее размыли бы учебную цель, чем улучшили решение.
