# Тестирование и запуск

Этот раздел объясняет, как во втором спринте организованы тесты, что именно они проверяют и почему выбранная структура проекта выглядит именно так.

## Зачем во втором спринте понадобился отдельный тестовый проект

В sprint 1 проект был больше про построение API и базовую архитектуру.  
Во sprint 2 появился отдельный слой бизнес-логики, который уже имеет смысл закреплять тестами:

- проверки существования ресурса;
- бизнес-валидация;
- фильтрация;
- пагинация.

Если такие вещи не тестировать, регрессия будет почти неизбежна даже в небольшом учебном проекте.

## Структура тестового проекта

Тесты вынесены в проект:

`EventManagementService.API.Tests`

Основные файлы:

- `EventManagementService.API.Tests/EventManagementService.API.Tests.csproj`
- `EventManagementService.API.Tests/Services/EventServiceCrudTests.cs`
- `EventManagementService.API.Tests/Services/EventServiceQueryTests.cs`
- `EventManagementService.API.Tests/Services/EventServiceValidationTests.cs`
- `EventManagementService.API.Tests/Services/EventTestData.cs`

## Почему тестовый проект расположен рядом с основным

Вариант с размещением рядом с основным проектом выбран из практического соображения:

- из корня репозитория удобно запускать `dotnet run`;
- из корня же удобно запускать `dotnet build` и `dotnet test`.

### Побочный эффект этой структуры

Так как основной `.csproj` лежит в корне репозитория, тестовые `.cs` файлы могли бы случайно попасть в компиляцию основного проекта.

Поэтому в `EventManagementService.API.csproj` используется:

```xml
<DefaultItemExcludes>$(DefaultItemExcludes);EventManagementService.API.Tests/**;tests/**</DefaultItemExcludes>
```

Это хороший практический пример настройки SDK-style проектов в .NET.

## Почему выбран `xUnit`

`xUnit` выбран по нескольким причинам:

- это стандартный и распространённый выбор для .NET;
- синтаксис тестов короткий и читаемый;
- `Fact` достаточно для текущих сценариев;
- тесты хорошо ложатся на стиль AAA.

В проекте не подключалась отдельная assertion-библиотека, потому что встроенных `Assert.*` хватает для текущего объёма логики.

## Что именно тестируется

Тесты сосредоточены на `EventService`, потому что это и есть основной носитель бизнес-правил sprint 2.

### Почему не тестируется `EventsController`

Задание требует покрыть именно бизнес-логику сервиса.  
Контроллер сейчас тонкий и в основном:

- маппит DTO;
- вызывает сервис;
- возвращает HTTP-ответ.

Самые ценные для проверки правила находятся именно в сервисном слое.

## Набор тестов

### 1. `EventServiceCrudTests`

Проверяет happy path CRUD:

- создание события;
- получение всех событий;
- получение по `id`;
- обновление существующего события;
- удаление существующего события.

Эти тесты нужны, чтобы закрепить базовое корректное поведение сервиса.

### 2. `EventServiceQueryTests`

Проверяет чтение списка:

- фильтрацию по названию;
- фильтрацию по диапазону дат;
- комбинированную фильтрацию;
- пагинацию;
- пустой результат.

Это ядро нового функционала sprint 2.

### 3. `EventServiceValidationTests`

Проверяет negative scenarios:

- запрос несуществующего события;
- обновление несуществующего события;
- удаление несуществующего события;
- создание события с пробельным названием;
- создание события с некорректными датами;
- обновление события с некорректными датами;
- некорректные параметры пагинации.

Эти тесты особенно важны, потому что именно они подтверждают правильную работу кастомных исключений и бизнес-валидации.

## Сколько тестов есть сейчас

На текущем этапе покрыто 18 test methods:

- 5 CRUD-сценариев;
- 5 query-сценариев;
- 8 validation/failure сценариев.

Это хороший уровень покрытия для учебного in-memory сервиса такого размера.

## Почему используется `EventTestData`

В тестовом проекте есть helper:

`EventManagementService.API.Tests/Services/EventTestData.cs`

Он нужен, чтобы:

- не дублировать создание `Event` во всех тестах;
- сделать Arrange-часть короче;
- повысить читаемость тестов.

Это маленькая, но полезная техника поддержки тестового кода.

## Почему в тестах используются фиксированные даты

В тестах не используется `DateTime.Now`.

Это важно, потому что:

- тесты становятся детерминированными;
- поведение не зависит от времени запуска;
- легче проверять фильтрацию и порядок страниц.

Для тестов на даты это обязательная практика.

## Принцип AAA

Все тесты написаны в стиле:

- **Arrange**
- **Act**
- **Assert**

Такой формат делает тесты понятными даже без чтения реализации.

### Почему это полезно

- проще увидеть, что именно подготавливается;
- легче понять, какое действие тестируется;
- быстрее находить ошибку, если тест падает.

## Что тесты говорят о дизайне кода

Сам факт, что `EventService` легко тестируется напрямую, означает:

- сервис не зависит от HTTP-контекста;
- бизнес-логика достаточно изолирована;
- архитектурное разделение между controller и service выполнено удачно.

Тестируемость здесь выступает индикатором качества дизайна.

## Как запускать проект

Из корня репозитория:

```bash
dotnet restore
dotnet build
dotnet run
```

## Как запускать тесты

Из корня репозитория:

```bash
dotnet test
```

Если нужно посмотреть только сборку тестов:

```bash
dotnet build
```

## Что проверить вручную через Swagger

Кроме автоматических тестов, полезно руками проверить:

1. `GET /api/events?title=dotnet`
2. `GET /api/events?from=...&to=...`
3. `GET /api/events?page=2&pageSize=2`
4. `GET /api/events/{bad-id}` → `404`
5. `POST` или `PUT` с `endAt <= startAt` → `400`
6. `POST` с отсутствующими обязательными полями → `400` от model validation

### Почему ручная проверка всё ещё нужна

Unit-тесты подтверждают поведение сервиса, но не заменяют визуальную проверку:

- Swagger-контрактов;
- формата ответов;
- поведения model binding;
- общего UX API.

## Что можно добавить в будущем

Если развивать проект дальше, логично добавить:

- интеграционные тесты через `WebApplicationFactory`;
- тесты контроллера;
- тесты самого middleware;
- покрытие edge cases вроде очень больших диапазонов дат, пустых строк и граничных страниц.

Но для sprint 2 текущий уровень уже хорошо соответствует заданию.

## Практический итог

Тестовый слой во втором спринте не декоративный.  
Он закрепляет именно те вещи, ради которых спринт и делался:

- перенос правил в сервис;
- появление query-логики;
- корректную обработку ошибок и граничных случаев.

Это делает проект значительно сильнее с точки зрения качества кода.
