# Обработка ошибок и валидация

Этот раздел посвящён одной из самых важных частей sprint 2: тому, как API реагирует на ошибки и почему разные типы ошибок обрабатываются разными механизмами.

## Общая схема

В проекте есть два источника ошибок:

1. **Ошибки model validation**  
   Возникают во время привязки DTO и проверки `DataAnnotations`.

2. **Ошибки бизнес-логики и остальные исключения**  
   Возникают внутри сервисов и другого прикладного кода.

Для единообразия используются два механизма:

- `InvalidModelStateResponseFactory` в `Program.cs`
- `ExceptionHandlingMiddleware`

Оба возвращают `ProblemDetails`.

## Middleware `ExceptionHandlingMiddleware`

Файл: `Middleware/ExceptionHandlingMiddleware.cs`

### Его задача

Middleware оборачивает обработку запроса в `try/catch`:

- если исключения нет — просто передаёт выполнение дальше;
- если исключение есть — логирует его и формирует ответ клиенту.

Это делает ошибку частью инфраструктуры, а не частной логики контроллера.

## Почему middleware лучше локального `try/catch`

Если писать `try/catch` в каждом action:

- код дублируется;
- ошибки оформляются по-разному;
- труднее поддерживать единый формат;
- контроллер начинает отвечать за инфраструктуру.

Middleware решает это централизованно.

## Какие исключения используются

### `BusinessValidationException`

Используется для нарушений правил предметной области:

- пустое название;
- `EndAt <= StartAt`;
- некорректный `page`;
- слишком большой `pageSize`.

Это не “сбой системы”, а ожидаемая ошибка бизнес-правил, поэтому она маппится на `400 Bad Request`.

### `NotFoundException`

Используется в случаях, когда ресурс отсутствует:

- нет события с указанным `id`;
- нечего обновлять;
- нечего удалять.

Это маппится на `404 Not Found`.

### Остальные исключения

Любая ошибка, которая не относится к этим типам, уходит в `500 Internal Server Error`.

Это важное поведение по умолчанию: неожиданные ошибки не должны утекать наружу как будто это “обычная” валидация.

## Отображение исключений в HTTP-статусы

Ключевой участок middleware — это логика сопоставления типов исключений и кодов ответа:

- `BusinessValidationException` → `400`
- `NotFoundException` → `404`
- всё остальное → `500`

Такой mapping прост, прозрачен и легко расширяется.

## Почему используется `ProblemDetails`

`ProblemDetails` даёт стандартную структуру ошибки:

- `type`
- `title`
- `status`
- `detail`
- `instance`

В проекте дополнительно используется:

- `traceId`

Это полезно, потому что:

- клиент получает предсказуемый ответ;
- логи и ответ можно соотнести между собой;
- Swagger и другие клиенты лучше работают со стандартным форматом.

## Почему добавлен `traceId`

`traceId` — это техническая, но очень полезная деталь.

Он нужен, чтобы:

- связать ответ клиента с логами сервера;
- быстрее искать конкретную ошибку;
- упростить диагностику.

Для учебного проекта это хороший пример того, как API может быть удобным не только для “пользователя”, но и для разработчика.

## Почему есть проверка `Response.HasStarted`

Если ответ уже начал отправляться клиенту, middleware не должен пытаться заменить его новым телом ошибки.

Поэтому используется защита:

- если `Response.HasStarted == true`, middleware логирует ситуацию и прекращает попытку модифицировать ответ.

Это аккуратная инфраструктурная практика, которую легко пропустить в упрощённых примерах.

## Почему вызывается `Response.Clear()`

Перед записью `ProblemDetails` текущий ответ очищается.

Это делается, чтобы:

- убрать частично сформированные данные;
- исключить смешивание старого и нового тела ответа;
- гарантировать чистый error-response.

Такой шаг особенно полезен, если исключение произошло не в самом начале обработки запроса.

## Почему используется `IProblemDetailsService`

В middleware внедряется:

```csharp
IProblemDetailsService problemDetailsService
```

Это интеграция с инфраструктурой ASP.NET Core.

### Преимущества

- используем стандартный сервис платформы;
- остаёмся ближе к встроенной модели ASP.NET Core;
- проще расширять поведение в будущем.

Если бы `ProblemDetails` сериализовался только вручную, код был бы чуть проще, но хуже интегрировался бы с платформой.

## Почему настраивается `AddProblemDetails()`

В `Program.cs` вызывается:

```csharp
builder.Services.AddProblemDetails();
```

Это регистрирует инфраструктуру `ProblemDetails` в DI и позволяет middleware использовать `IProblemDetailsService`.

## Model validation и почему middleware недостаточно

Очень важный момент для понимания ASP.NET Core:

- DataAnnotations на DTO проверяются framework’ом автоматически;
- при `[ApiController]` ASP.NET Core может вернуть `400` ещё до входа в action;
- в этот момент никакого исключения может не быть.

Это значит, что middleware не является единственной точкой для формирования ошибок.

Именно поэтому в `Program.cs` настраивается:

```csharp
builder.Services.Configure<ApiBehaviorOptions>(...)
```

## Что делает `InvalidModelStateResponseFactory`

Эта настройка заменяет стандартный ответ на невалидную модель своим вариантом.

В проекте она создаёт `ValidationProblemDetails` и возвращает:

- `400 Bad Request`
- `application/problem+json`
- `traceId`

### Почему это важно

Без неё было бы два разных формата ошибок:

1. для исключений из middleware;
2. для автоматической model validation.

С этой настройкой API становится единообразнее.

## Разница между request validation и business validation

Это одна из ключевых учебных идей sprint 2.

### Request validation

Проверяет, что HTTP-запрос корректно сформирован:

- переданы обязательные поля;
- `page >= 1`;
- `pageSize` в диапазоне `1..100`.

Часть этой логики живёт в DTO через `DataAnnotations`.

### Business validation

Проверяет правила предметной области:

- название не должно быть пустым или пробельным;
- дата окончания должна быть позже даты начала;
- сервис не должен работать с несуществующим событием как с существующим.

Эта логика живёт в `EventService`.

### Почему это разделение важно

Если смешать два уровня, будет трудно понять:

- что относится к HTTP-контракту;
- что относится к предметной области;
- что нужно тестировать через controller/integration tests;
- что нужно тестировать как unit-тест сервиса.

## Интересные участки кода

### 1. Кастомные исключения с тремя конструкторами

Это сделано по классическим рекомендациям .NET:

- конструктор по умолчанию;
- конструктор с `message`;
- конструктор с `message + innerException`.

Для учебного проекта это полезно, потому что показывает правильный шаблон построения собственных exception-классов.

### 2. Логирование в middleware

Middleware пишет в лог:

- метод;
- путь;
- `traceId`;
- `x-request-id`, если передан.

Это делает обработчик ошибок не просто “красивым”, а ещё и диагностически полезным.

### 3. Разные поля `title` и `detail`

В `ProblemDetails` `title` — короткое типизированное описание ошибки,  
а `detail` — конкретное сообщение для данной ситуации.

Это хорошая модель, потому что:

- `title` можно использовать как общий классификатор;
- `detail` — как конкретику для пользователя или разработчика.

## Что можно было бы сделать иначе

### 1. Использовать `app.UseExceptionHandler(...)`

ASP.NET Core имеет встроенный exception handler middleware.  
Но в учебном проекте собственный middleware полезнее, потому что:

- он нагляднее;
- его проще разобрать руками;
- он лучше показывает, как устроен pipeline.

### 2. Использовать одну общую `ValidationException`

Можно было бы ограничиться одним типом, но разделение на `BusinessValidationException` и `NotFoundException` делает API выразительнее.

### 3. Сделать единый список `ProblemDetails` factories

Это возможно, но для текущего масштаба проекта было бы избыточно.

## Практический итог

Во sprint 2 проект получил не просто обработку ошибок, а полноценную модель:

- HTTP-ошибки единообразны;
- бизнес-ошибки отделены от технических;
- model validation встроена в общий стиль API;
- логирование помогает разбираться в сбоях.

Это одна из самых ценных частей проекта с точки зрения архитектурной культуры.
