# Введение и обзор спринта 2

## Назначение второго спринта

Если в первом спринте проект решал базовую задачу CRUD для сущности `Event`, то во втором спринте он стал заметно ближе к реальному Web API.

Появились три важных направления:

1. **Надёжность API**  
   Ошибки теперь обрабатываются централизованно, а клиент получает единообразный JSON-ответ.

2. **Удобство чтения данных**  
   `GET /api/events` умеет не только возвращать все события, но и фильтровать их по названию и датам, а также отдавать страницы результата.

3. **Подтверждение корректности через тесты**  
   Основная бизнес-логика `EventService` покрыта unit-тестами.

## Что изменилось относительно sprint 1

Во втором спринте проект эволюционировал в нескольких точках.

### 1. Контроллер стал тоньше

В sprint 1 контроллер сам принимал решения:

- когда вернуть `400`;
- когда вернуть `404`;
- какие проверки считать бизнес-валидацией;
- как обрабатывать список событий.

Во sprint 2 контроллер в основном:

- принимает DTO;
- вызывает сервис;
- маппит результат в `EventResponse`;
- полагается на middleware и сервис для обработки ошибок.

Это важный архитектурный шаг, потому что HTTP-слой перестаёт дублировать бизнес-правила.

### 2. Появилась единая стратегия ошибок

Сейчас проект использует:

- `ExceptionHandlingMiddleware` для необработанных исключений;
- `ProblemDetails` как формат ответа;
- `BusinessValidationException` для бизнес-ошибок;
- `NotFoundException` для отсутствующих ресурсов;
- `InvalidModelStateResponseFactory` для ошибок DataAnnotations.

В результате клиент видит единый стиль ответа и не зависит от того, где именно возникла ошибка.

### 3. `GET /api/events` стал полноценным query endpoint

Вместо простого “вернуть всё” endpoint поддерживает:

- `title` — поиск по названию;
- `from` — нижнюю границу начала события;
- `to` — верхнюю границу окончания события;
- `page` — номер страницы;
- `pageSize` — размер страницы.

Это переводит API от демонстрационного CRUD к более реалистичному чтению данных.

### 4. Появился тестовый проект

Тесты вынесены в отдельный проект `EventManagementService.API.Tests`.

Он покрывает:

- happy path сценарии CRUD;
- фильтрацию и пагинацию;
- сценарии с `404` и бизнес-валидацией.

## Ключевые результаты спринта

По факту реализации проект теперь умеет:

- централизованно возвращать `400`, `404`, `500`;
- фильтровать события по нескольким условиям через LINQ;
- пагинировать результат через `Skip` и `Take`;
- валидировать бизнес-правила в сервисе, а не в контроллере;
- поддерживать `dotnet build`, `dotnet run` и отдельный тестовый проект для `dotnet test`.

## Что особенно полезно изучить в этом спринте

### 1. Разделение типов валидации

В проекте теперь есть два разных слоя проверки данных:

- **model validation** через `DataAnnotations`;
- **business validation** через `EventService`.

Это один из самых полезных практических моментов для понимания ASP.NET Core.

### 2. Разделение transport logic и business logic

Контроллер знает про HTTP и DTO.  
Сервис знает про правила предметной области и работу с коллекцией.  
Middleware знает про инфраструктуру ошибок.

Такое разделение важнее конкретной бизнес-задачи проекта.

### 3. Контракт как код + тесты

Во втором спринте поведение сервиса уже не просто “написано в коде”, а закреплено тестами.  
Это хороший момент, чтобы начать воспринимать тесты как часть спецификации.

## Почему этот спринт важен для учебного проекта

Именно здесь проект переходит от “API работает” к “API сделан инженерно аккуратно”.

Без sprint 2 приложение было бы:

- менее предсказуемым для клиента;
- труднее тестируемым;
- слабее масштабируемым по логике;
- менее пригодным для нормального ревью.

С sprint 2 код становится более структурированным и ближе к тому, как устроены реальные backend-приложения.
