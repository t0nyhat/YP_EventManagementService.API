# Фильтрация и пагинация

В sprint 2 endpoint `GET /api/events` превратился из простого “вернуть весь список” в полноценный query endpoint.

Этот раздел объясняет:

- как устроен входной контракт;
- как работает LINQ-логика в `EventService`;
- почему сортировка и snapshot важны;
- как формируется пагинированный ответ.

## Входной контракт: `GetEventsQuery`

Файл: `Dtos/GetEventsQuery.cs`

DTO содержит пять параметров:

- `Title`
- `From`
- `To`
- `Page`
- `PageSize`

### Семантика параметров

#### `title`

Опциональный строковый параметр.

Используется как:

- регистронезависимый поиск;
- частичное совпадение.

То есть запрос `?title=dotnet` найдёт и `DotNet Meetup`, и `DotNet Advanced`.

#### `from`

Опциональная нижняя граница.

Логика:

- событие попадает в результат, если `StartAt >= From`.

#### `to`

Опциональная верхняя граница.

Логика:

- событие попадает в результат, если `EndAt <= To`.

#### `page`

Номер страницы. По умолчанию `1`.

#### `pageSize`

Размер страницы. По умолчанию `10`.

В проекте дополнительно ограничен диапазоном `1..100`, чтобы не позволять бессмысленно большие страницы.

## Почему query-параметры оформлены отдельным DTO

Вместо сигнатуры вида:

```csharp
GetAllEvents(string? title, DateTime? from, DateTime? to, int page = 1, int pageSize = 10)
```

используется:

```csharp
GetAllEvents([FromQuery] GetEventsQuery query)
```

### Это даёт несколько преимуществ

1. Сигнатура action остаётся компактной.
2. Swagger красиво показывает параметры как единый контракт.
3. Легче расширять endpoint новыми параметрами.
4. Удобнее валидировать значения через `DataAnnotations`.

## Где живёт логика фильтрации

Фильтрация реализована не в контроллере, а в `Services/EventService.cs`.

Это важно по двум причинам:

- так требует задание;
- так правильнее архитектурно.

Контроллер лишь передаёт `query` в сервис и маппит результат в `EventResponse`.

## Алгоритм `GetEvents(...)`

Метод `GetEvents(GetEventsQuery query)` можно мысленно разложить на этапы:

1. Проверка параметров пагинации.
2. Снятие snapshot текущего списка под `lock`.
3. Построение LINQ-запроса.
4. Условное применение фильтров.
5. Явная сортировка.
6. Подсчёт общего количества элементов.
7. Применение `Skip` и `Take`.
8. Формирование `PaginatedResult<Event>`.

## Почему используется snapshot

Сервис работает с in-memory коллекцией `_events`, а сам сервис — singleton.

Чтобы не держать `lock` на всём этапе LINQ-обработки, делается копия:

```csharp
snapshot = _events.ToList();
```

Дальше уже можно безопасно выполнять:

- фильтрацию;
- сортировку;
- пагинацию.

Это делает метод аккуратнее с точки зрения конкурентного доступа.

## Как применяются фильтры

### Фильтр по названию

Если `Title` не пустой и не состоит только из пробелов:

```csharp
filteredEvents = filteredEvents.Where(eventItem =>
    eventItem.Title.Contains(query.Title, StringComparison.OrdinalIgnoreCase));
```

Здесь важно два момента:

- `Contains` даёт частичное совпадение;
- `OrdinalIgnoreCase` делает поиск регистронезависимым.

### Фильтр по началу периода

Если передан `From`:

```csharp
eventItem.StartAt >= query.From.Value
```

### Фильтр по окончанию периода

Если передан `To`:

```csharp
eventItem.EndAt <= query.To.Value
```

### Все фильтры работают как логическое И

Это значит, что событие должно пройти все применённые условия сразу.

Например, если указаны и `title`, и `from`, и `to`, то событие попадёт в результат только если:

- его название подходит;
- дата начала не раньше `from`;
- дата окончания не позже `to`.

## Почему перед пагинацией задаётся сортировка

В сервисе используется:

```csharp
filteredEvents = filteredEvents.OrderBy(eventItem => eventItem.StartAt);
```

Это очень важная деталь.

### Без сортировки пагинация формально работала бы, но:

- порядок элементов зависел бы от внутреннего состояния списка;
- контракт API был бы менее предсказуемым;
- тестировать страницы было бы хуже.

### Почему выбрана сортировка по `StartAt`

Для событий это естественный порядок:

- сначала более ранние мероприятия;
- затем более поздние.

Такой порядок проще воспринимать клиенту.

## Как считается пагинация

После фильтрации и сортировки:

```csharp
var totalCount = filteredEvents.Count();
var items = filteredEvents
    .Skip((query.Page - 1) * query.PageSize)
    .Take(query.PageSize)
    .ToArray();
```

### Что здесь важно

#### `totalCount`

Считается **до** пагинации.  
Это размер отфильтрованного набора, а не длина текущей страницы.

#### `Skip`

Пропускает элементы предыдущих страниц.

Например:

- `Page = 1`, `PageSize = 10` → `Skip(0)`
- `Page = 2`, `PageSize = 10` → `Skip(10)`

#### `Take`

Берёт только нужное количество элементов для текущей страницы.

## Выходной контракт: `PaginatedResult<T>`

Файл: `Dtos/PaginatedResult.cs`

Текущий контракт содержит:

- `Items`
- `Page`
- `Count`
- `TotalCount`

### Почему именно так

Задание требует вернуть:

- массив самих событий;
- номер текущей страницы;
- количество элементов на текущей странице;
- общее количество событий.

Поэтому:

- `Count` — это фактическое количество элементов в текущем ответе;
- `TotalCount` — это размер всего отфильтрованного результата.

## Почему `Count`, а не просто `PageSize`

`PageSize` — это количество, которое **запросили**.  
`Count` — это количество, которое **реально вернули**.

Это разные вещи.

Например:

- `PageSize = 10`
- на последней странице осталось только `3` элемента

В таком случае `Count = 3`, и именно это ближе к формулировке задания.

## Почему сервис дополнительно валидирует `Page` и `PageSize`

Хотя `GetEventsQuery` уже содержит `DataAnnotations`, сервис всё равно проверяет:

- `Page >= 1`
- `PageSize >= 1`
- `PageSize <= 100`

### Зачем дублировать

Потому что сервис должен оставаться корректным не только при HTTP-вызове.

Если кто-то вызовет `GetEvents(...)` напрямую из кода, бизнес-контракт всё равно будет защищён.

Это хорошая практика: полагаться не только на transport-level validation.

## Интересные участки кода

### 1. Сортировка до `Skip` / `Take`

Это маленькая, но очень важная инженерная деталь.  
Без неё пагинация была бы менее устойчивой и хуже тестировалась бы.

### 2. Игнорирование пустого `title`

Фильтр по названию применяется только если строка не пустая и не пробельная.  
Это делает API более дружелюбным и снижает число “случайно странных” запросов.

### 3. Материализация `ToArray()`

Страница материализуется в массив перед возвратом.  
Это делает результат завершённым и предсказуемым, а не “ленивым перечислением”, зависящим от дальнейшего состояния запроса.

## Как это покрыто тестами

Сценарии находятся в `EventServiceQueryTests.cs`:

- фильтрация по названию;
- фильтрация по датам;
- комбинированная фильтрация;
- пагинация;
- пустой результат.

Тесты не только проверяют “что что-то вернулось”, но и закрепляют:

- порядок результатов;
- корректный `Count`;
- корректный `TotalCount`.

## Практический итог

С точки зрения sprint 2 именно `GetEvents(...)` делает проект заметно более зрелым:

- появляется выразительный query-контракт;
- логика чтения данных становится контролируемой;
- API перестаёт быть “верни весь список целиком”.

Это один из лучших участков проекта для изучения LINQ в прикладном Web API.
