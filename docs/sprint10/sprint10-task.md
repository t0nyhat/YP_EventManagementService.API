Задание
Ваш сервис становится популярным! Нагрузка растёт, и вам приходит задача добавить на главную страницу виджет «топ-10 самых популярных событий». Запрос без авторизации, его будут делать все посетители — каждый раз обращаться в базу слишком дорого. Решение — добавить Redis и кешировать результат по TTL.
Заодно вы закешируете получение события по идентификатору, но с другим подходом: данные меняются, поэтому нужно продумать стратегию (инвалидация при записи или обновление кеша вместе с базой) и обосновать её в README.
В результате выполнения проектной работы вы:
подключите Redis к сервису событий и зарегистрируете соединение в DI;
выделите абстракцию кеша в слой Application, а реализацию на Redis — в слой Infrastructure;
закешируете получение события по идентификатору и список топ-10 самых популярных событий;
настроите TTL и реализуете выбранную стратегию обновления кеша при создании, обновлении и удалении события;
учтёте обновление кеша в обработчике Kafka-сообщений, если он влияет на данные события;
покроете логику кеширования unit-тестами: попадание в кеш, промах, инвалидация;
опишете стратегию кеширования и её обоснование в README.

Проект использует C#, .NET 8 и выше, ASP.NET Core Web API.
Код приложения хранится в том же публичном GitHub-репозитории.
Тесты запускаются командой dotnet test и успешно проходят.

Кеш для отдельного события обновляется или инвалидируется при его изменении или удалении; кеш топа живёт по TTL.

Как работать над заданием
Этап 1. Подготовка к работе

Убедитесь, что проектная работа девятого спринта успешно завершена.
Переключитесь на ветку main вашего репозитория и выполните git pull для синхронизации.
Создайте новую ветку sprint-10 из ветки main и переключитесь на неё.
Всю работу по этому проекту ведите в ветке sprint-10.
Этап 2. Подключение NuGet-пакета и настройка соединения

Добавьте NuGet-пакет для работы с Redis StackExchange.Redis в проект Events по управлению событиями.
Вынесите строку подключения в конфигурацию (appsettings.json). Зарегистрируйте соединение в DI: клиент Redis — это тяжёлый потокобезопасный объект, его нужно создавать один раз и переиспользовать на протяжении всего жизненного цикла приложения.
Этап 3. Абстракция кеша

Изолируйте Redis за интерфейсом, чтобы слой Application не зависел от конкретной библиотеки. Интерфейс определите в Application, реализацию — в Infrastructure. Минимальный набор операций: получить значение по ключу, записать с временем жизни, удалить.
Позаботьтесь об устойчивости: если Redis недоступен, ошибки нужно логировать, но не пробрасывать — кеш должен деградировать без ошибки для клиента, запрос пойдёт напрямую в базу данных.
Этап 4. Кеширование данных

Реализуйте паттерн Cache-Aside для двух сценариев:
Получение события по идентификатору (GET /events/{id})
При чтении сначала проверяйте кеш по ключу вида event:{id}. Если данных нет, запросите результат из базы и сохраните результат в кеш с TTL.
Топ-10 самых популярных событий (GET /events/top)
Новый эндпоинт, который возвращает 10 событий с наибольшим процентом проданных мест. Процент продаж считается по формуле: (total_seats - available_seats) / total_seats. Добавьте метод в репозиторий, соответствующий метод в сервисе и эндпоинт в API-слое. Кеш сохраняйте по ключу events:top10.
Этап 5. Инвалидация кеша и обоснование стратегии

Для топ-10 кеш достаточно обновлять по TTL: это рейтинговый агрегат, небольшое устаревание здесь некритично. Явная инвалидация при каждом бронировании была бы избыточной — список всё равно меняется нечасто.
Для отдельного события устаревание заметнее, поэтому выберите один из двух подходов:
Инвалидация при записи — при изменении события соответствующий ключ удаляется из кеша. Следующий читающий запрос обратится к базе и прогреет кеш заново.
Обновление при записи — при изменении события кеш обновляется вместе с базой данных.
Оба подхода допустимы, главное, чтобы при обновлении и удалении события ключ event:{id} менялся.
В сервисе событий есть обработчик Kafka-сообщений. Если он изменяет данные события, не забудьте обновить или инвалидировать кеш и там.
Обратите внимание на порядок операций: изменения нужно сначала сохранить в базу данных, и только потом менять кеш. Если выполнение оборвётся между этими двумя шагами, база останется в актуальном состоянии — кеш при следующем запросе просто обновится.
Опишите выбранную стратегию в README: что кешируется и почему, как выбраны значения TTL, что происходит при изменении данных.
Этап 6. Конфигурация и Docker Compose

Добавьте параметры кеша — строку подключения и значения TTL — в appsettings.json.
Добавьте контейнер Redis в docker-compose.yml.
В прошлом спринте мы показывали пример docker-compose.yml с сервисами Kafka, Zookeeper и тремя базами данных. Дополните его контейнером Redis:
services:
  # ... существующие сервисы ...

  redis:
    image: redis:7.2-alpine
    container_name: eventapi-redis
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  # ... существующие тома ...
Обратите внимание: внутри сети Docker сервисы обращаются друг к другу по имени контейнера, поэтому строка подключения — redis:6379, а не localhost:6379. Значение из переменной окружения Redis__ConnectionString автоматически переопределит соответствующий параметр в appsettings.json.
Этап 7. Тесты

Напишите unit-тесты для сервиса, подменяя кеш и репозиторий заглушками. Проверьте следующие сценарии:
при попадании в кеш репозиторий не вызывается;
при промахе данные берутся из репозитория и сохраняются в кеш;
при мутирующих операциях кеш обновляется или инвалидируется в соответствии с выбранной стратегией.
Этап 8. Проверка и оформление

Запустите систему через docker compose up --build и проверьте сценарий целиком: кеш работает, данные актуализируются после изменений.
Убедитесь, что сервис запускается и работает при недоступном Redis.
Добавьте в README раздел с описанием и обоснованием стратегии кеширования.
Сделайте финальный commit и push всех изменений в ветку sprint-10 на GitHub.
Этап 9. Сдача работы

Создайте pull request из ветки sprint-10 в ветку main вашего репозитория.
Скопируйте ссылку на созданный pull request.
В уроке с проектом вставьте ссылку на pull request в поле для ссылки и нажмите «Отправить».
Ревьюер проверит вашу работу и оставит комментарии в pull request, если потребуются правки.
После того как правки по всем комментариям будут внесены, ревьюер одобрит pull request.
Выполните слияние изменений в ветку main.
