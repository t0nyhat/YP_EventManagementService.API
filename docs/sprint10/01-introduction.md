# Введение в sprint 10

## 1. Цель спринта

После микросервисной декомпозиции sprint 9 сервис Events получает два часто вызываемых публичных read-сценария:

1. `GET /events/{id}` — карточка конкретного события;
2. `GET /events/top` — виджет десяти самых популярных событий.

Оба endpoint не требуют авторизации, поэтому число чтений может значительно превышать число изменений. Обращаться к PostgreSQL при каждом запросе необязательно: результат можно временно хранить в Redis и отдавать быстрее, снижая нагрузку на основную БД.

## 2. Роль Redis в системе

Redis здесь — **производный best-effort кеш**, а не ещё одно постоянное хранилище:

- PostgreSQL остаётся единственным источником истины;
- потеря всех Redis-ключей не приводит к потере бизнес-данных;
- при промахе кеш восстанавливается из БД;
- недоступность Redis не должна превращаться в недоступность Events API;
- корректность записи в БД важнее успешной инвалидации кеша.

Из этого следует порядок операций для всех мутаций: сначала сохранить бизнес-изменение, затем удалить устаревший ключ. Обратный порядок создавал бы окно, в котором другой запрос мог бы прогреть кеш ещё не подтверждёнными данными.

## 3. Почему выбран Cache-Aside

При Cache-Aside приложение само управляет кешем:

```text
чтение: cache -> hit или database -> cache -> response
запись: database commit -> invalidate cache
```

Паттерн подходит проекту по трём причинам:

- кешируются только два явно выбранных read-пути, а не весь репозиторий;
- DTO попадает в Redis только тогда, когда его действительно запросили;
- при сбое Redis тот же use case естественно продолжает работу через PostgreSQL.

Альтернатива write-through потребовала бы синхронно поддерживать второе хранилище при каждой записи. Для необязательного кеша это усложняет отказоустойчивость без заметной пользы.

## 4. Две разные политики актуальности

У отдельного события и агрегированного топа разные требования:

| Данные | Ключ | TTL | Политика |
|---|---|---:|---|
| Карточка события | `event:{id}` | 10 минут | инвалидация после каждой успешной записи плюс TTL как страховка |
| Топ-10 | `events:top10` | 1 минута | только TTL, без активной инвалидации |

Карточка события видна пользователю напрямую: устаревшие название, даты или число мест заметны, поэтому ключ удаляется после CRUD и подтверждённого бронирования. Топ — рейтинговая проекция, где небольшое отставание допустимо; удалять общий ключ после каждого бронирования означало бы почти постоянно пересчитывать дорогой агрегат и свело бы пользу кеша к минимуму.

## 5. Связь с асинхронным потоком sprint 9

Events меняется не только через HTTP. `BookingConfirmedHandler` после Kafka-сообщения уменьшает `AvailableSeats`, а значит, ранее кешированная карточка события становится устаревшей.

Инвалидация добавлена и в этот путь: обработчик сначала одной транзакцией сохраняет изменение Event и inbox-запись, затем удаляет `event:{eventId}`. Ветки, где событие не менялось (`duplicate`, `EventNotFound`, `EventAlreadyStarted`, `NotEnoughSeats`), кеш не трогают.

## 6. Что осталось прежним

- Границы Users / Events / Bookings и отдельные PostgreSQL-базы не менялись.
- Kafka, Outbox, Inbox, DLT и eventual consistency продолжают работать по правилам sprint 9.
- JWT и авторизация прежние: чтение Events анонимно, CRUD доступен только `Admin`.
- Clean Architecture сохранена: Application знает абстракцию кеша, но не знает StackExchange.Redis.
- Общий `GET /events` с фильтрацией и пагинацией не кешируется.

## 7. Осознанный scope

В спринт не входят distributed lock против cache stampede, Redis Cluster/Sentinel, pub/sub-инвалидация, кеширование 404, кеширование общего списка событий и персистентность Redis. Эти механизмы нужны только при подтверждённой эксплуатационной необходимости; текущая реализация остаётся небольшой, проверяемой и безопасно деградирует.
