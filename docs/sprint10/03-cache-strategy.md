# Стратегия кеширования и согласованность

## 1. Cache-Aside для отдельного события

Алгоритм `EventService.GetEventByIdAsync(id)`:

1. построить ключ через `EventCacheKeys.ForEvent(id)`;
2. запросить `EventResponse` из `ICacheService`;
3. hit → сразу вернуть DTO, репозиторий не вызывается;
4. miss → прочитать `Event` из PostgreSQL;
5. если события нет — вернуть `404`, ничего не записывая в Redis;
6. преобразовать сущность в `EventResponse`, положить с `EventTtl`, вернуть клиенту.

Кеширование 404 (negative caching) сознательно не используется. После создания события с тем же идентификатором старый отрицательный результат мог бы временно скрывать существующие данные; для учебного API проще и безопаснее кешировать только найденные события.

## 2. Cache-Aside для топ-10

Алгоритм `EventService.GetTopEventsAsync()`:

1. прочитать `EventResponse[]` по константному ключу `events:top10`;
2. hit → вернуть read-only обёртку, не вызывая репозиторий;
3. miss → запросить у репозитория максимум 10 строк;
4. преобразовать результат в массив DTO;
5. сохранить массив с `TopEventsTtl` и вернуть read-only обёртку.

Пустой массив — валидный результат и тоже кешируется. Иначе пустая БД порождала бы запрос к PostgreSQL при каждом обращении к популярному публичному endpoint.

## 3. Ключи и payload

| Сценарий | Ключ | Значение | Особенность |
|---|---|---|---|
| Событие по id | `event:{guid:D}` | `EventResponse` | GUID в lowercase, с дефисами |
| Топ событий | `events:top10` | `EventResponse[]` | не более 10 элементов, пустой массив допустим |

Все ключи строятся в [`EventCacheKeys`](../../src/EventManagementService.Events.Application/Caching/EventCacheKeys.cs), поэтому формат не дублируется строковыми литералами по use cases. Централизованный [`CacheJson`](../../src/EventManagementService.Events.Infrastructure/Caching/CacheJson.cs) обеспечивает одинаковый camelCase-формат при записи и чтении.

## 4. Почему TTL различаются

### `EventTtl = 10 минут`

Основной механизм актуальности карточки — активная инвалидация. Длинный TTL повышает hit rate для редко изменяемого события, а также ограничивает максимальное время устаревания, если удаление ключа не удалось из-за сбоя Redis или процесс остановился сразу после commit БД.

### `TopEventsTtl = 1 минута`

Топ зависит от всех событий и меняется после каждого успешного бронирования. Инвалидировать агрегат на каждой записи означало бы часто пересчитывать SQL-рейтинг и уменьшило бы пользу кеширования. Одноминутный TTL прямо ограничивает допустимое отставание виджета и при этом объединяет множество запросов пользователей в один запрос к БД на интервал.

Оба значения вынесены в секцию `Cache` и валидируются на старте как строго положительные.

## 5. Матрица инвалидации

| Операция | `event:{id}` | `events:top10` | Обоснование |
|---|---|---|---|
| cache miss на `GET /events/{id}` | записать с `EventTtl` | не менять | прогрев карточки |
| cache miss на `GET /events/top` | не менять | записать с `TopEventsTtl` | прогрев агрегата |
| create | удалить после commit | не менять | единое правило write paths; топ обновится по TTL |
| update | удалить после commit | не менять | не отдавать старые поля карточки |
| delete | удалить после commit | не менять | не отдавать удалённое событие по id |
| `BookingConfirmed: Processed` | удалить после commit Event + Inbox | не менять | изменилось `AvailableSeats` |
| duplicate / skipped Kafka message | не менять | не менять | данные Event не изменились |

Даже при create выполняется защитное удаление: 404 не кешируется, поэтому ключ обычно отсутствует, но единое правило «успешная запись → invalidation» проще проверять и безопаснее при будущих изменениях.

## 6. Почему инвалидация, а не обновление при записи

Выбран подход **invalidate-on-write**:

- запись в БД не обязана одновременно собирать и сериализовать DTO;
- после update/delete нет риска положить в Redis значение, не соответствующее закоммиченному состоянию;
- следующий реальный читатель прогревает кеш, поэтому не создаются невостребованные записи;
- один и тот же механизм подходит CRUD и Kafka-обработчику.

Цена — первый запрос после изменения идёт в PostgreSQL. Для событий, которые изменяются значительно реже, чем читаются, это подходящий компромисс.

## 7. Порядок «БД, затем кеш»

Для update/delete порядок принципиален:

```text
изменить сущность -> SaveChangesAsync -> RemoveAsync(event key)
```

Если `SaveChangesAsync` завершился ошибкой, инвалидация не выполняется и кеш продолжает соответствовать старому состоянию БД. Если commit успешен, а удаление Redis не удалось, база всё равно корректна; устаревшая кеш-запись ограничена `EventTtl`.

Нельзя сначала удалить ключ, а затем сохранять БД: конкурентный GET между этими операциями увидит miss, прочитает старую строку и снова положит её в кеш.

## 8. Kafka и граница commit

Успешный `BookingConfirmedHandler` одной транзакцией сохраняет уменьшение мест и Inbox, после чего вызывает:

```csharp
await cache.RemoveAsync(EventCacheKeys.ForEvent(message.EventId), CancellationToken.None);
```

Используется `CancellationToken.None`: после commit нельзя пропустить удаление только потому, что host уже начал останавливаться. Иначе Kafka-offset мог бы не закоммититься, сообщение пришло бы повторно, но Inbox распознал бы дубль и ветка дубликата уже не выполнила бы инвалидацию. Сам Redis-адаптер best-effort, поэтому инфраструктурная ошибка всё равно не прерывает обработчик.

## 9. Деградация при сбоях Redis

Контракт `ICacheService` определяет поведение отказов:

- ошибка чтения → warning и `null`, то есть обычный cache miss;
- ошибка записи → warning и no-op;
- ошибка удаления → warning и no-op;
- некорректный JSON → warning, best-effort удаление повреждённого ключа и miss;
- `OperationCanceledException` не проглатывается: отмена запроса остаётся отменой, а не маскируется под отказ кеша.

Таким образом, недоступный Redis увеличивает нагрузку и latency, но не меняет HTTP-семантику и не делает PostgreSQL-данные недоступными.

## 10. Осознанные ограничения и развитие

- **Cache stampede:** несколько одновременных miss могут параллельно прочитать БД и записать один ключ. Distributed lock/single-flight не добавлялись до появления реальной проблемы.
- **Короткое окно stale read:** между commit и удалением ключа конкурентный запрос может получить старое значение; invalidate-on-write без распределённой транзакции не даёт строгой линейризуемости.
- **Нет pub/sub:** при одном общем Redis удаление ключа видно всем инстансам; локальных L1-кешей, требующих рассылки инвалидации, нет.
- **Версионирование payload:** `CacheJson.Options` централизует формат, но несовместимое изменение DTO должно сопровождаться версией ключей или очисткой кеша при выкладке.
- **Redis не персистентен:** это допустимо, потому что все значения восстанавливаются из PostgreSQL.
