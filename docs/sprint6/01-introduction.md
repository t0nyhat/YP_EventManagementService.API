# Спринт 6: Миграции, репозитории и PostgreSQL integration tests

## Назначение спринта

В sprint 5 проект уже хранил данные в PostgreSQL через EF Core, но архитектурно оставались две зоны роста:

- создание схемы через `EnsureCreated` вместо миграций;
- прямой доступ сервисов к `DbContext`, из-за чего data access и бизнес-логика смешивались.

Цель sprint 6: перейти на полноценный migration-first подход и выделить репозиторный слой, сохранив существующий API-контракт и поведение бронирований.

## Что было сделано

1. Добавлены интерфейсы и реализации репозиториев событий и бронирований.
2. `EventService` и `BookingService` переведены с `DbContext` на репозитории.
3. `BookingProcessingBackgroundService` обновлен для работы через репозитории в scoped-контексте.
4. Создана первая миграция `InitialCreate`.
5. Startup-путь переведен на `Database.Migrate()`.
6. Создан отдельный integration test проект на PostgreSQL Testcontainers.
7. Добавлены тесты репозиториев и тесты схемы/ограничений на уровне PostgreSQL.

## Почему это важно

- Миграции дают управляемую эволюцию схемы БД между окружениями.
- Репозитории уменьшают связность сервисов с ORM-деталями.
- Реальный PostgreSQL в интеграционных тестах проверяет ограничения, которые InMemory-провайдер не воспроизводит.
- Появляется более прозрачная граница между бизнес-правилами и инфраструктурой хранения.

## Главные учебные выводы

1. `EnsureCreated` подходит для быстрых прототипов, но миграции лучше для развивающейся схемы.
2. Сервис должен выражать бизнес-операции, а не SQL/ORM детали.
3. Интеграционные тесты должны проверять поведение на той же СУБД, что и runtime.
4. Проверка схемы (FK, каскады, ограничения) это отдельный слой валидации качества.
