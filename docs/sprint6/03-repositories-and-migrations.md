# Репозитории и миграции в sprint 6

## 1. Контракты репозиториев

### `IEventRepository`

Основные операции:

- чтение списка событий с фильтрацией/пагинацией;
- получение события по `id`;
- добавление/удаление;
- сохранение изменений.

### `IBookingRepository`

Основные операции:

- получение брони по `id`;
- получение pending ID для фоновой обработки;
- добавление брони;
- сохранение изменений.

## 2. Реализации на EF Core

`EventRepository` и `BookingRepository` инкапсулируют EF Core-запросы.

Особенности:

- списковые read-only запросы используют `AsNoTracking()`;
- бизнес-валидация не дублируется в репозиториях и остается в сервисах;
- сохранение выполняется через `SaveChangesAsync` в рамках scoped `DbContext`.

## 3. Миграции

В спринте создана первая миграция `InitialCreate`, которая фиксирует схему таблиц:

- `events`;
- `bookings`;
- FK между `bookings.event_id` и `events.id`.

В runtime используется `Database.Migrate()`, поэтому схема приводится к актуальному состоянию по истории миграций.

## 4. Почему это лучше `EnsureCreated`

`EnsureCreated` не ведет историю изменений схемы.

Миграции дают:

- управляемые schema changes;
- прозрачные diff между версиями;
- безопасный путь обновления БД в разных окружениях.

## 5. Ограничения и поведение на уровне БД

В интеграционных тестах проверяется, что схема реально применилась:

- FK-ограничение отклоняет бронь на несуществующее событие;
- `ON DELETE CASCADE` работает для зависимых бронирований;
- ограничения длины колонок приводят к `DbUpdateException` при нарушении.
