# Архитектурные решения

В этом разделе рассматриваются ключевые архитектурные аспекты проекта: слои приложения, внедрение зависимостей (DI), middleware, выбор типов интерфейсов и возвращаемых значений, а также обоснование принятых решений.

## Слои приложения (Layered Architecture)

Проект следует упрощённой многослойной архитектуре, типичной для ASP.NET Core Web API:

1. **Presentation Layer (Контроллеры)**  
   - `Controllers/EventsController` — обрабатывает HTTP-запросы, выполняет маршрутизацию, валидацию входных данных и преобразование между DTO и доменными моделями.  
   - Контроллер не содержит бизнес-логики, делегируя её сервисному слою.

2. **Business Logic Layer (Сервисы)**  
   - `Services/IEventService` (интерфейс) и `Services/EventService` (реализация) — содержат всю логику работы с событиями: создание, чтение, обновление, удаление, а также управление in‑memory хранилищем.  
   - Сервисный слой изолирован от деталей HTTP и может быть повторно использован в других контекстах (например, в фоновых задачах).

3. **Data Access Layer (Модели и хранилище)**  
   - `Models/Event` — доменная модель, представляющая бизнес-сущность «Событие».  
   - В текущей реализации слой доступа к данным сводится к работе с коллекцией `List<Event>` внутри `EventService`. В реальном проекте здесь располагались бы репозитории, Entity Framework DbContext или клиенты внешних API.

4. **DTO Layer (Слой передачи данных)**  
   - `Dtos/` — содержит классы для сериализации/десериализации запросов и ответов API.  
   - Отделение DTO от доменных моделей позволяет:
     - скрыть внутреннюю структуру модели от клиента,
     - добавлять или удалять поля без изменения контракта API,
     - применять атрибуты валидации, специфичные для API.

## Внедрение зависимостей (Dependency Injection)

ASP.NET Core имеет встроенный контейнер DI, который активно используется в проекте.

### Регистрация сервисов

В `Program.cs` выполняется следующая регистрация:

```csharp
builder.Services.AddSingleton<IEventService, EventService>();
```

**Почему выбран Singleton?**  
- `EventService` хранит состояние в private поле `_events` (список событий).  
- Для обеспечения согласованности данных все запросы должны работать с одним экземпляром сервиса.  
- Singleton гарантирует, что коллекция `_events` будет единой на протяжении всего времени жизни приложения.  
- Альтернативы:  
  - **Scoped** — подошёл бы, если бы использовалась база данных с контекстом, привязанным к запросу.  
  - **Transient** — привел бы к созданию нового экземпляра сервиса для каждого обращения, и данные «терялись» бы между запросами.

### Внедрение в контроллер

Контроллер принимает зависимость через конструктор:

```csharp
public EventsController(IEventService eventService) : ControllerBase
```

Это соответствует принципу **инверсии зависимостей (Dependency Inversion)** — контроллер зависит от абстракции (`IEventService`), а не от конкретной реализации. Такое решение упрощает модульное тестирование (можно подменить сервис заглушкой) и позволяет в будущем заменить реализацию без изменения кода контроллера.

## Middleware в конвейере HTTP

Middleware — это компоненты, которые обрабатывают HTTP-запросы и ответы. В `Program.cs` настроен следующий конвейер:

1. **Swagger/OpenAPI** (`UseSwagger`, `UseSwaggerUI`, `MapOpenApi`)  
   - Добавляется только в режиме Development (`if (app.Environment.IsDevelopment())`).  
   - Предоставляет интерактивный UI для тестирования API и документацию в формате OpenAPI.

2. **HTTPS Redirection** (`UseHttpsRedirection`)  
   - Перенаправляет все HTTP-запросы на HTTPS, повышая безопасность.  
   - В разработке это может быть избыточно, но является рекомендуемой практикой для production.

3. **Маршрутизация контроллеров** (`MapControllers`)  
   - Активирует систему маршрутизации ASP.NET Core, которая сопоставляет URL с методами контроллера.

**Почему не использованы другие middleware?**  
- **Аутентификация/авторизация** — не требуется по условиям учебного проекта.  
- **Логирование** — можно добавить через `app.UseMiddleware<LoggingMiddleware>()` или встроенные провайдеры.  
- **Обработка исключений** — в реальном проекте стоит добавить `app.UseExceptionHandler` для централизованного возврата ошибок в формате JSON.

## Выбор типов интерфейсов и возвращаемых значений

### Интерфейс IEventService

```csharp
public interface IEventService
{
    IEnumerable<Event> GetAllEvents();
    Event? GetEventById(Guid id);
    Event CreateEvent(Event newEvent);
    Event? UpdateEvent(Guid id, Event updatedEvent);
    bool DeleteEvent(Guid id);
}
```

**Обоснование:**

- `IEnumerable<Event>` для `GetAllEvents()` — возвращает перечисление, что позволяет лениво обрабатывать данные (хотя в текущей реализации используется `.ToList()`).  
- `Event?` (nullable) для `GetEventById` и `UpdateEvent` — явно указывает, что метод может вернуть `null` если событие не найдено. Это лучше, чем выбрасывать исключение, т.к. отсутствие события является ожидаемым сценарием.  
- `bool` для `DeleteEvent` — возвращает `true` при успешном удалении, `false` если события не существовало. Альтернатива — возвращать `void` и игнорировать отсутствие, но тогда клиент не узнает, был ли ресурс удалён.  
- `Event` для `CreateEvent` — возвращает созданный объект с заполненным `Id` (сгенерированным на сервере). Это соответствует принципу REST: клиент получает полное представление созданного ресурса.

### Возвращаемые типы действий контроллера

Контроллер использует `ActionResult<T>` — тип, предоставляемый ASP.NET Core, который позволяет комбинировать возвращаемые данные с кодами состояния HTTP.

Пример:
```csharp
public ActionResult<EventResponse> GetEventById(Guid id)
{
    var eventItem = eventService.GetEventById(id);
    if (eventItem is null)
    {
        return NotFound(new { message = $"Событие с id {id} не найдено." });
    }
    return Ok(MapToResponse(eventItem));
}
```

**Почему ActionResult<T>, а не IActionResult?**  
- `ActionResult<T>` обеспечивает строгую типизацию возвращаемого значения в Swagger-документации.  
- Позволяет одновременно указывать тип успешного ответа (`EventResponse`) и возможные ошибки через атрибуты `[ProducesResponseType]`.  
- Упрощает unit-тестирование, т.к. можно извлечь значение через `.Value`.

## Потокобезопасность

Поскольку `EventService` является Singleton и хранит данные в памяти, необходимо защитить коллекцию `_events` от одновременного изменения в многопоточной среде (ASP.NET Core обрабатывает запросы параллельно).

**Реализация:**

```csharp
private readonly object _lock = new object();

public IEnumerable<Event> GetAllEvents()
{
    lock (_lock)
    {
        return _events.ToList();
    }
}
```

**Почему lock, а не ConcurrentCollection?**  
- `ConcurrentBag` или `ConcurrentDictionary` обеспечивают потокобезопасность на уровне отдельных операций, но не гарантируют атомарность составных действий (например, «проверить существование → обновить»).  
- `lock` проще для понимания и даёт полный контроль над критической секцией.  
- В учебном проекте с низкой нагрузкой `lock` является приемлемым решением. В production-системах с высокой конкурентностью стоит рассмотреть более оптимизированные подходы (например, `ReaderWriterLockSlim` или базу данных с транзакциями).

## Альтернативные подходы

1. **Использование репозитория** — выделить отдельный слой `IRepository<Event>` для абстракции доступа к данным. Это позволило бы легко заменить in‑memory хранилище на базу данных.

2. **MediatR и CQRS** — разделение команд и запросов через библиотеку MediatR упростило бы масштабирование и добавление пайплайнов поведения (логирование, валидация, кэширование).

3. **FluentValidation** — вместо атрибутов DataAnnotations можно использовать библиотеку FluentValidation для более сложных правил валидации.

4. **AutoMapper** — для автоматического преобразования между `Event` и `EventResponse` можно применить AutoMapper, уменьшив ручной mapping.

Эти подходы не были использованы, чтобы сохранить проект простым и сфокусированным на базовых концепциях ASP.NET Core.
