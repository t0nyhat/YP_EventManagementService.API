# Модели, DTO и валидация

В этом разделе подробно рассматриваются доменные модели, Data Transfer Objects (DTO) и применяемые стратегии валидации. Понимание различий между этими сущностями и правил их использования критически важно для построения корректного и безопасного API.

## Доменная модель (Domain Model)

### Класс `Event`

Расположение: `Models/Event.cs`

```csharp
public class Event
{
    public Guid Id { get; set; }
    public required string Title { get; set; }
    public string? Description { get; set; }
    public DateTime StartAt { get; set; }
    public DateTime EndAt { get; set; }
}
```

**Назначение:**  
Доменная модель представляет бизнес-сущность «Событие» внутри приложения. Она содержит данные и может включать поведение (хотя в данном проекте поведение вынесено в сервис).

**Особенности:**

- `Id` — уникальный идентификатор типа `Guid`. Генерируется на стороне сервера при создании события. Клиент не может указать свой `Id` (это предотвращает коллизии и повышает безопасность).
- `Title` — обязательное поле, помеченное модификатором `required` (C# 11+). Это гарантирует, что свойство будет инициализировано при создании объекта.
- `Description` — необязательное поле (`string?`), может быть `null`.
- `StartAt` и `EndAt` — дата и время начала и окончания события. Оба поля обязательны (не nullable). Бизнес-правило: `EndAt` должно быть позже `StartAt`; это правило проверяется на уровне контроллера, а не в модели.

**Почему модель не содержит атрибутов валидации?**  
Доменная модель предназначена для внутреннего использования. Валидация входных данных выполняется на границе API (в DTO), а бизнес-правила — в сервисе или контроллере. Такое разделение позволяет:

- избежать дублирования проверок,
- сохранить модель чистой от инфраструктурных деталей,
- использовать одну и ту же модель в разных контекстах (например, в фоновых задачах, где валидация DataAnnotations не требуется).

## Data Transfer Objects (DTO)

DTO — это объекты, которые передаются между клиентом и API. Они служат для:

1. **Изоляции внутренней структуры** — клиент не знает о полях доменной модели, которые не должны быть видны.
2. **Оптимизации payload** — можно включать только необходимые поля.
3. **Валидации** — атрибуты валидации применяются именно к DTO.

В проекте определены три DTO:

### 1. `CreateEventRequest`

Используется для операции **POST /api/events**.

```csharp
public class CreateEventRequest
{
    [Required(ErrorMessage = "Название события обязательно!")]
    public required string Title { get; set; }

    public string? Description { get; set; }

    [Required(ErrorMessage = "Дата начала события обязательна!")]
    public DateTime? StartAt { get; set; }

    [Required(ErrorMessage = "Дата окончания события обязательна!")]
    public DateTime? EndAt { get; set; }
}
```

**Особенности:**

- Все обязательные поля помечены атрибутом `[Required]` с кастомными сообщениями на русском языке.
- `StartAt` и `EndAt` объявлены как `DateTime?` (nullable), чтобы атрибут `[Required]` мог отловить отсутствие значения. После прохождения валидации в контроллере они приводятся к `DateTime` (через `.Value`).
- **Нет поля `Id`** — идентификатор генерируется сервером, клиент не может его указать. Это соответствует принципу идемпотентности и безопасности.

### 2. `UpdateEventRequest`

Используется для операции **PUT /api/events/{id}**.

```csharp
public class UpdateEventRequest
{
    [Required(ErrorMessage = "Название события обязательно")]
    public required string Title { get; set; }

    public string? Description { get; set; }

    [Required(ErrorMessage = "Дата начала события обязательна")]
    public DateTime? StartAt { get; set; }

    [Required(ErrorMessage = "Дата окончания события обязательна!")]
    public DateTime? EndAt { get; set; }
}
```

**Отличия от `CreateEventRequest`:**  
Структурно идентичен, но семантически используется для обновления существующего ресурса. `Id` передаётся через URL, а не в теле запроса.

### 3. `EventResponse`

Используется для **ответов** на GET, POST, PUT.

```csharp
public class EventResponse
{
    public Guid Id { get; set; }

    [Required]
    public required string Title { get; set; }

    public string? Description { get; set; }

    [Required]
    public DateTime StartAt { get; set; }

    [Required]
    public DateTime EndAt { get; set; }
}
```

**Особенности:**

- Содержит `Id` — после создания или запроса клиент получает идентификатор для последующих операций.
- Поля `StartAt` и `EndAt` — не nullable (`DateTime`), т.к. в ответе они всегда присутствуют.
- Атрибуты `[Required]` используются не для валидации, а для документирования контракта (Swagger учитывает их при генерации схемы).

## Валидация

Валидация в ASP.NET Core выполняется автоматически, если контроллер помечен атрибутом `[ApiController]`. Этот атрибут включает:

- **Автоматическую проверку модели** (Model State Validation).
- **Возврат HTTP 400 с деталями ошибок**, если модель невалидна.

### Уровни валидации

1. **Валидация на основе атрибутов (DataAnnotations)**  
   Проверяет наличие обязательных полей, формат данных и т.д. Например, если клиент отправит `{ "title": null }`, будет возвращена ошибка:
   ```json
   {
     "type": "https://tools.ietf.org/html/rfc7231#section-6.5.1",
     "title": "One or more validation errors occurred.",
     "status": 400,
     "errors": {
       "Title": ["Название события обязательно!"]
     }
   }
   ```

2. **Кастомная бизнес-валидация**  
   Выполняется вручную в контроллере. Например, проверка того, что `EndAt > StartAt`:
   ```csharp
   if (request.EndAt <= request.StartAt)
   {
       return BadRequest(new { message = "Дата окончания должна быть позже даты начала события." });
   }
   ```
   Эта проверка не может быть выражена через DataAnnotations (требуется сравнение двух полей), поэтому реализована явно.

3. **Валидация существования ресурса**  
   Для операций PUT и DELETE контроллер сначала проверяет, существует ли событие с указанным `Id`. Если нет — возвращается 404.

### Почему валидация находится в контроллере, а не в сервисе?

- **Разделение ответственности**: Контроллер отвечает за корректность входных данных и HTTP-специфичные проверки (например, формат даты). Сервис работает с уже валидированными данными и реализует бизнес-логику.
- **Гибкость**: Если в будущем понадобится добавить GraphQL или gRPC endpoint, сервис сможет использоваться повторно, а валидация будет выполнена на уровне нового адаптера.

### Альтернативные подходы к валидации

- **FluentValidation** — библиотека, позволяющая описывать сложные правила в отдельных классах. Поддерживает цепочки условий, асинхронную валидацию и локализацию. В учебном проекте не используется для простоты.
- **Validation Attributes в модели** — можно было бы добавить `[Range]`, `[StringLength]` и т.д. прямо в DTO. Это увеличило бы детализацию ошибок, но также усложнило бы поддержку.

## Маппинг между DTO и моделью

Поскольку DTO и модель имеют схожие поля, требуется преобразование:

- **Из `CreateEventRequest` в `Event`** — выполняется в контроллере вручную:
  ```csharp
  var eventItem = new Event
  {
      Title = request.Title,
      Description = request.Description,
      StartAt = request.StartAt!.Value,
      EndAt = request.EndAt!.Value
  };
  ```
  Использование `.Value` безопасно, т.к. к этому моменту валидация уже гарантирует, что поля не `null`.

- **Из `Event` в `EventResponse`** — выполняется приватным методом `MapToResponse`:
  ```csharp
  private static EventResponse MapToResponse(Event eventItem)
  {
      return new EventResponse
      {
          Id = eventItem.Id,
          Title = eventItem.Title,
          Description = eventItem.Description,
          StartAt = eventItem.StartAt,
          EndAt = eventItem.EndAt
      };
  }
  ```

**Почему не используется AutoMapper?**  
Для проекта с малым количеством полей ручной маппинг проще и прозрачнее. AutoMapper добавил бы зависимость и скрыл бы преобразования, что могло бы затруднить отладку. В больших проектах AutoMapper становится оправдан.

## Итог

- **Модель** — внутреннее представление данных, без валидации.
- **DTO** — контракт API, содержащий атрибуты валидации и адаптированный под нужды клиента.
- **Валидация** — комбинация автоматической (DataAnnotations) и ручной (бизнес-правила) проверок на уровне контроллера.

Такой подход обеспечивает чистоту кода, безопасность и удобство расширения.
