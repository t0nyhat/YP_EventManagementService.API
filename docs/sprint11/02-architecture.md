# Архитектура наблюдаемости

## 1. Общая схема

В Sprint 11 бизнес-архитектура системы не меняется: Users, Events и Bookings остаются независимыми сервисами со своими базами данных. Наблюдаемость добавлена как инфраструктурный слой вокруг HTTP-конвейера и доступа к данным.

Каждый API формирует три вида телеметрии:

| Сигнал | Получатель | Способ доставки |
|---|---|---|
| Метрики | Prometheus | Prometheus опрашивает `/metrics` по pull-модели |
| Трейсы | Jaeger | API отправляет OTLP-данные по gRPC |
| Логи | Docker stdout/stderr | Serilog пишет одну JSON-запись на событие |

Grafana читает метрики из Prometheus и предоставляет единый дашборд для всех трех API.

## 2. Границы Clean Architecture

Пакеты OpenTelemetry и Serilog подключены только к Presentation-проектам:

- `EventManagementService.Users.Presentation`;
- `EventManagementService.Events.Presentation`;
- `EventManagementService.Bookings.Presentation`.

Domain и Application не зависят от конкретных экспортеров, Prometheus, Jaeger или формата логов. Инструментирование использует стандартные точки интеграции ASP.NET Core, `HttpClient`, EF Core и .NET runtime, поэтому бизнес-код не содержит вызовов мониторинга.

Такое расположение сохраняет направление зависимостей: наблюдаемость относится к внешнему слою приложения и может быть заменена без изменения бизнес-правил.

## 3. Направление потоков данных

### 3.1. Метрики

Каждый сервис публикует анонимный endpoint `/metrics`. Prometheus с интервалом 15 секунд обращается к контейнерам по внутренним адресам:

| Job | Target |
|---|---|
| `users-service` | `users-api:8080/metrics` |
| `events-service` | `events-api:8080/metrics` |
| `bookings-service` | `bookings-api:8080/metrics` |

Внешний порт для `/metrics` не требуется: endpoint доступен Prometheus внутри Docker-сети и одновременно может проверяться через опубликованные HTTP-порты API.

### 3.2. Трейсы

Все API отправляют спаны в `jaeger:4317` через OTLP/gRPC. В Jaeger один запрос представлен деревом:

1. серверный HTTP-спан ASP.NET Core;
2. дочерние SQL-спаны EF Core;
3. клиентские HTTP-спаны, если сервис выполняет исходящий HTTP-запрос.

Имя сервиса задается ресурсным атрибутом `service.name`, поэтому в Jaeger доступны три независимых сервиса: `users-service`, `events-service` и `bookings-service`.

### 3.3. Логи

Serilog пишет компактный JSON в стандартный вывод контейнера. Docker отвечает только за доставку и хранение вывода; отдельный log backend в состав Sprint 11 не входит. Поля `TraceId` и `SpanId` позволяют сопоставить запись журнала с запросом в Jaeger.

## 4. Конфигурация ресурсов

Конфигурация каждого API содержит одинаковую структуру и различается именем сервиса:

| Параметр | Назначение | Пример в Docker Compose |
|---|---|---|
| `OpenTelemetry:ServiceName` | Значение `service.name` в метриках и трейсах | `events-service` |
| `Otlp:Endpoint` | Адрес OTLP collector | `http://jaeger:4317` |

Оба параметра проверяются при старте. Пустое имя сервиса, невалидный URI или схема, отличная от HTTP/HTTPS, считаются ошибкой конфигурации. Это предотвращает запуск с анонимными трейсами или молча неработающим экспортером.

## 5. HTTP-конвейер

Обычный запрос проходит через request logging, обработку исключений, HTTPS redirection, аутентификацию, авторизацию и endpoint приложения. Для `/metrics` используются отдельные ветви:

- запрос не попадает в Serilog request log;
- для него не выполняется HTTPS redirection;
- endpoint разрешает анонимный доступ;
- встроенные HTTP-метрики ASP.NET Core отключены для самого endpoint;
- ASP.NET Core tracing filter не создает спан.

Исключение `/metrics` предотвращает рекурсивное измерение мониторинга и не засоряет логи и трейсы регулярными scrape-запросами Prometheus.

Request logging расположен перед обработчиком исключений. Благодаря этому итоговый HTTP-статус, включая `500`, фиксируется после завершения всего конвейера, а не до преобразования исключения в ответ.

## 6. Поведение при недоступности backend

Prometheus, Jaeger и Grafana не находятся на критическом пути обработки бизнес-запроса:

- отсутствие Prometheus означает только прекращение scrape;
- временная недоступность Jaeger приводит к потере части экспортируемых трейсов после исчерпания буфера;
- недоступность Grafana не влияет на сбор метрик Prometheus;
- запись JSON-логов продолжает работать независимо от monitoring-контейнеров.

Это важное свойство: сбой системы наблюдаемости не должен превращаться в отказ API.

## 7. Контейнерная топология

Полный стек состоит из 12 контейнеров:

| Группа | Контейнеры |
|---|---|
| API | Users, Events, Bookings |
| Хранилища | три PostgreSQL, Redis |
| Messaging | Zookeeper, Kafka |
| Observability | Prometheus, Jaeger, Grafana |

Пользовательские интерфейсы monitoring-стека опубликованы на локальной машине:

| Компонент | URL |
|---|---|
| Prometheus | `http://localhost:9090` |
| Jaeger | `http://localhost:16686` |
| Grafana | `http://localhost:3000` |

Grafana использует provisioned datasource `prometheus` с внутренним URL `http://prometheus:9090`, поэтому после `docker compose up` ручная настройка не требуется.

## 8. Граница безопасности

Monitoring UI и учетные данные Grafana `admin/admin` предназначены для локальной разработки. В production необходимо как минимум:

- закрыть UI аутентификацией и сетевыми правилами;
- вынести учетные данные в secret storage;
- ограничить доступ к `/metrics` на уровне сети;
- настроить retention и защищенное хранилище телеметрии;
- использовать TLS и аутентификацию для OTLP.
