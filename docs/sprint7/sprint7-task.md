Задание
В этом спринте вы реорганизуете текущий сервис бронирований, разбивая проект на четыре отдельных по принципам чистой архитектуры: Domain, Application, Infrastructure, Presentation. Каждый проект — отдельная сборка с чётко очерченной ответственностью, а зависимости между ними направлены только «внутрь». 
Затем вы перенесёте бизнес-логику из контроллеров и сервисов в Application и Domain, оставив в Presentation только HTTP-обвязку. 
Инфраструктурные зависимости (БД, репозитории, внешние сервисы) подключите через интерфейсы портов, которые внедряются в Application через DI.
В результате выполнения проектной работы вы:
разделите солюшен на четыре отдельных проекта — Domain, Application, Infrastructure, Presentation и настроите зависимости между ними;
перенесёте бизнес-логику из контроллеров и сервисов в Application и/или Domain;
введёте интерфейсы портов в Application и реализуете адаптеры в Infrastructure;
настроите DI-контейнер для подключения инфраструктурных реализаций через интерфейсы (composition root в Presentation);
Требования и функциональность
Проект использует C#, .NET 8 и выше, ASP.NET Core Web API.
Код приложения хранится в том же публичном GitHub-репозитории.
Проект собирается и запускается стандартными средствами (dotnet build, dotnet run).
Тесты запускаются командой dotnet test и успешно проходят.
Swagger доступен и корректно отображает все эндпоинты.
Солюшен разделён на четыре отдельных проекта: Domain, Application, Infrastructure, Presentation.
Application не зависит от Infrastructure напрямую — только через интерфейсы.
Composition root (регистрация всех зависимостей) находится в Presentation.
Как работать над заданием
Этап 1. Подготовка к работе

Убедитесь, что проектная работа шестого спринта успешно завершена.
Переключитесь на ветку main вашего репозитория и выполните git pull для синхронизации.
Создайте новую ветку sprint-7 из ветки main и переключитесь на неё.
Всю работу по этому проекту ведите в ветке sprint-7.
Этап 2. Создание проектов и настройка зависимостей

Добавьте в солюшен три новых class library проекта и один оставьте как точку входа (веб-проект). Разделение на отдельные сборки принципиально: компилятор не даст случайно нарушить направление зависимостей.
Состав каждого слоя:
Domain — доменные сущности, value objects, доменные исключения. Не зависит ни от чего внешнего.
Application — use cases, сервисы, интерфейсы портов (репозитории, шлюзы), DTO. Зависит только от Domain.
Infrastructure — реализации портов: репозитории, DbContext, внешние клиенты. Зависит от Application и Domain.
Presentation — контроллеры/Minimal API эндпоинты, HTTP-маппинг, регистрация зависимостей. Зависит от Application и Infrastructure.
Схема приложения.
Настройте <ProjectReference> между проектами так, чтобы направление зависимостей соответствовало схеме выше.
Важно! Убедитесь, что у проекта Application нет ссылки на Infrastructure — только на Domain. Это ключевое правило чистой архитектуры: бизнес-логика не должна знать о том, как именно хранятся данные или с какими внешними системами идёт интеграция. Любое нарушение этого правила обесценивает всё разделение.  
Этап 3. Перенос в Domain

Перенесите в слой Domain всё, что описывает предметную область и не зависит от технологий:
доменные сущности и перечисления;
доменные исключения (исключения, которые отражают нарушение бизнес-правил — например, нет доступных мест, ресурс не найден).
Убедитесь, что Domain не импортирует ничего из фреймворков (ASP.NET Core, EF Core и т. д.).
Этап 4. Перенос в Application

Перенесите в слой Application бизнес-логику и абстракции:
интерфейсы сервисов и их реализации (use cases);
интерфейсы портов — абстракции для доступа к данным (репозитории) и внешним сервисам. Application определяет, что ему нужно от инфраструктуры, через эти интерфейсы;
DTO (объекты передачи данных между слоями);
фоновые сервисы, если их логика относится к Application (в зависимости от вашего решения).
Application не должен содержать ни одной ссылки на Infrastructure.
Этап 5. Перенос в Infrastructure

Перенесите в слой Infrastructure реализации, которые зависят от внешних технологий:
реализации интерфейсов репозиториев с использованием DbContext;
сам DbContext, конфигурации маппинга сущностей, миграции;
любые другие адаптеры к внешним системам.
Добавьте extension-метод (или аналогичный способ) для регистрации всех Infrastructure-зависимостей в DI-контейнере.
Этап 6. Обновление Presentation

После выделения слоёв Presentation должен содержать только:
эндпоинты/контроллеры — получить HTTP-запрос, вызвать нужный обработчик/сервис в Application, вернуть ответ;
обработчик глобальных исключений с маппингом доменных исключений в HTTP-статусы;
composition root в Program.cs — регистрация всех зависимостей через DI. Вызывайте extension-методы из Application и Infrastructure, чтобы Program.cs оставался компактным.
Убедитесь, что в эндпоинтах не осталось бизнес-логики.
Этап 7. Обновление тестов

Обновите <ProjectReference> в тестовых проектах: они должны ссылаться на нужные проекты (обычно Application и Infrastructure), а не на монолитный Presentation-проект.
Обновите using-директивы в тестах в соответствии с новыми пространствами имён.
Убедитесь, что все тесты проходят успешно (dotnet test).
Этап 8. Проверка и оформление

Проверьте приложение через Swagger — создайте событие, создайте бронь, получите данные.
Убедитесь, что зависимости слоёв соблюдены: Application не зависит от Infrastructure.
Обновите README.md: 
опишите новую структуру проекта и назначение каждого слоя;
при необходимости добавьте инструкцию по созданию новых миграций с учётом новой структуры.
Убедитесь, что: 
проект собирается и запускается без ошибок;
все тесты проходят успешно.
Сделайте финальный commit и push всех изменений в ветку sprint-7 на GitHub.
Этап 9. Сдача работы

Создайте pull request из ветки sprint-7 в ветку main вашего репозитория.
Скопируйте ссылку на созданный pull request.
В уроке с проектом вставьте ссылку на pull request в поле для ссылки и нажмите «Отправить».
Ревьюер проверит вашу работу и оставит комментарии в pull request, если потребуются правки.
После того как правки по всем комментариям будут внесены, ревьюер одобрит pull request.
Выполните слияние изменений в ветку main.
Чек-лист проверки для ревью
Работа возвращается без проверки, если:

Нет ссылки на репозиторий или репозиторий приватный/недоступен.
Проект не собирается (dotnet build падает).
Проект не запускается (dotnet run падает).
Тесты не запускаются (dotnet test падает).
Нет обновлённого README с описанием изменений.

README содержит описание новой структуры.
Хорошие практики (необязательно для зачёта):

Тестовые проекты ссылаются на конкретные слои, а не на весь проект целиком.
Пространства имён соответствуют структуре слоёв и читаются однозначно.
