Задание
В этом спринте вы расширите доменную логику бронирований, добавив набор бизнес-правил: запрет бронирования событий из прошлого, ограничение на количество активных броней у одного пользователя и возможность администратора отменять чужие брони и управлять событиями. 
Для поддержки этих правил вы введёте сущность User с хранением учётных данных и свяжете её с Booking.
Затем вы добавите минимальный контур JWT-аутентификации: эндпоинт для регистрации, для получения токена по логину и паролю, middleware для проверки токена и авторизационные политики для ролей. 
В системе будут две роли: Admin и User. Администратор управляет событиями — создаёт, редактирует, удаляет их и может отменять любые брони. Обычный пользователь может только бронировать события и отменять собственные брони.
В результате выполнения проектной работы вы:
реализуете доменные правила бронирования: запрет бронирования прошедшего события, ограничение активных броней на пользователя, возможность администратора отменять чужие брони;
добавите сущность пользователя (логин, хеш пароля, роль), свяжете её с бронированием и обеспечите передачу идентификатора пользователя в сценариях бронирования и отмены;
реализуете регистрацию нового пользователя с выбором роли и выдачу JWT-токена по учётным данным;
настроите JWT-аутентификацию в Web API и обеспечите доступ к данным пользователя из claims;
настроите авторизацию: ограничите управление событиями ролью Admin, добавьте проверку владельца при отмене брони;
покроете реализованные правила и сценарии авторизации тестами (юнит и/или интеграционными на ваш выбор).
Требования и функциональность
Проект использует C#, .NET 8 и выше, ASP.NET Core Web API.
Код приложения хранится в том же публичном GitHub-репозитории.
Проект собирается и запускается стандартными средствами (dotnet build, dotnet run).
Тесты запускаются командой dotnet test и успешно проходят.
Swagger доступен и корректно отображает все эндпоинты.
Добавлена сущность User с полями логин, хеш пароля и роль (Admin / User).
Booking связан с User через поле UserId.
Доменные правила инкапсулированы в Application-слое и покрыты тестами.
POST /auth/register — регистрирует пользователя с указанной ролью (User по умолчанию, можно передать Admin); 204 No Content при успехе, 400 при ошибке валидации; доступен без токена.
POST /auth/login — принимает учётные данные и возвращает JWT-токен (200 OK); 404 при неверных учётных данных; доступен без токена.
POST /events/{id}/book — создаёт бронь (202 Accepted); требует аутентификации (401 без токена); 400 — событие уже началось, 404 — событие не найдено, 409 — нет доступных мест или превышен лимит броней.
GET /bookings/{id} — возвращает данные брони (200 OK); требует аутентификации (401); 404 — бронь не найдена.
DELETE /bookings/{id} — отменяет бронь (204 No Content); требует аутентификации (401); 403 — нет прав, 404 — бронь не найдена.
POST /events/, PUT /events/{id}, DELETE /events/{id} — доступны только роли Admin; 401 без токена, 403 для обычного пользователя.
Пользователь может отменить только свою бронь; администратор — любую.
Как работать над заданием
Этап 1. Подготовка к работе

Убедитесь, что проектная работа седьмого спринта успешно завершена.
Переключитесь на ветку main вашего репозитория и выполните git pull для синхронизации.
Создайте новую ветку sprint-8 из ветки main и переключитесь на неё.
Всю работу по этому проекту ведите в ветке sprint-8.
Этап 2. Подключение NuGet-пакетов

Для работы с JWT вам понадобятся два пакета: один для генерации токенов (подключается в Infrastructure), другой — для их проверки в middleware (подключается в Presentation).
Убедитесь, что решение собирается без ошибок командой dotnet build.
Этап 3. Расширение модели данных

В системе появляется пользователь. Внесите в модель следующие изменения:
Добавьте перечисление ролей с двумя значениями: User и Admin.
Добавьте сущность пользователя с полями: идентификатор, логин, хеш пароля и роль. Придерживайтесь тех же принципов инкапсуляции, что и в остальных сущностях проекта.
Свяжите бронирование с пользователем: добавьте поле UserId и обновите метод создания брони — он теперь должен принимать идентификатор пользователя.
Добавьте в бронирование метод отмены, который переводит его в статус Cancelled. Продумайте защиту от повторной отмены.
Добавьте значение Cancelled в перечисление статусов брони.
Добавьте доменные исключения для каждого нового бизнес-правила: бронирование прошедшего события, превышение лимита активных броней, отсутствие прав на операцию.
Этап 4. Компоненты безопасности

Реализуйте два независимых компонента:
Хеширование паролей. Реализуйте компонент для хеширования строки и проверки соответствия пароля хешу. Достаточно алгоритма SHA-256 из стандартной библиотеки System.Security.Cryptography:
var bytes = SHA256.HashData(Encoding.UTF8.GetBytes(password));
return Convert.ToHexString(bytes); 
Генерация JWT-токена. Реализуйте сервис, который по данным пользователя (идентификатор, логин, роль) формирует подписанный JWT-токен. Вынесите параметры токена (секрет, издатель, аудиторию, время жизни) в appsettings.json.
Этап 5. Обновление бизнес-логики и базы данных

Сервис бронирований. Внесите изменения в существующую логику управления бронированиями: 
при создании брони принимайте и сохраняйте идентификатор пользователя;
запретите бронирование события, которое уже началось (400);
ограничьте количество активных броней одного пользователя, у пользователя не может быть больше 10 бронирований, при превышении возвращайте 409;
добавьте операцию отмены брони с проверкой прав: пользователь может отменить только свою бронь, администратор — любую (403 при нарушении).
Сервис пользователей. Реализуйте компоненты для работы с пользователями: 
регистрация: сохранить пользователя с хешированным паролем;
вход: найти пользователя по логину, проверить пароль, вернуть токен.
Схема базы данных. Настройте маппинг EF Core для новых сущностей:
уникальный индекс на поле логина пользователя;
внешний ключ из бронирования на пользователя.
Создайте новую миграцию. Убедитесь, что миграция добавляет таблицу пользователей и колонку с идентификатором пользователя в таблицу бронирований.
Этап 6. Обновление API и авторизация

Добавьте параметры JWT в appsettings.json: секретный ключ, издателя, аудиторию и время жизни токена.
Подключите JWT-аутентификацию и авторизацию в Program.cs. Убедитесь, что middleware аутентификации и авторизации включены в пайплайн.
Добавьте эндпоинты для аутентификации: 
POST /auth/register принимает логин, пароль и необязательное поле role (User по умолчанию). Для удобства тестирования передача Admin допустима. Доступен без токена.
POST /auth/login принимает учётные данные и возвращает JWT-токен, доступен без токена.
Защитите существующие эндпоинты: 
POST /events/{id}/book, GET /bookings/{id} и DELETE /bookings/{id} требуют аутентификации; идентификатор текущего пользователя читайте из claims и передавайте в сервис.
POST /events/, PUT /events/{id}, DELETE /events/{id} доступны только администраторам; используйте атрибут [Authorize(Roles = "Admin")].
Добавьте маппинг новых исключений в обработчик ошибок: нет прав → 403, событие в прошлом → 400, лимит броней → 409.
Этап 7. Обновление тестов

Обновите существующие тесты с учётом изменившихся сигнатур (операции бронирования теперь требуют идентификатора пользователя).
Добавьте тесты, покрывающие новые бизнес-правила:
попытка забронировать прошедшее событие приводит к ошибке;
при достижении лимита активных броней новая бронь не создаётся;
лимиты разных пользователей не влияют друг на друга.
Этап 8. Проверка и оформление

Запустите приложение и проверьте через Swagger: 
зарегистрируйте нового пользователя;
получите токен через логин и вставьте его в Swagger (кнопка Authorize);
попробуйте создать событие без токена (ожидается 401) и с токеном обычного пользователя (ожидается 403);
войдите как администратор, создайте событие, создайте бронь, отмените её.
Убедитесь, что все тесты проходят успешно (dotnet test).
Обновите README.md: 
опишите ролевую модель и разграничение прав;
добавьте инструкцию по получению JWT-токена через Swagger;
опишите настройку секрета JWT в конфигурации и рекомендацию использовать безопасное значение в продакшне.
Сделайте финальный коммит и пуш всех изменений в ветку sprint-8 на GitHub.
Этап 9. Сдача работы

Создайте pull request из ветки sprint-8 в ветку main вашего репозитория.
Скопируйте ссылку на созданный pull request.
Вставьте ссылку на pull request в поле для ссылки и нажмите «Отправить».
Ревьюер проверит вашу работу. Он оставит комментарии в pull request, если потребуются правки.
После того как правки по всем комментариям будут внесены, ревьюер одобрит pull request.
Выполните слияние изменений в ветку main.
