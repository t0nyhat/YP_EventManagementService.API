# Введение в sprint 8

## 1. Цель спринта

Sprint 8 расширяет сервис бронирований тремя связанными направлениями:

1. **доменные бизнес-правила** бронирования и отмены;
2. **пользователи и роли** — сущность `User`, связь с бронированием;
3. **JWT-аутентификация и авторизация** — регистрация, логин, защита эндпоинтов по ролям и владению.

В отличие от прошлых спринтов, основная сложность здесь не в количестве эндпоинтов, а в **связности изменений**: авторизацию нельзя сделать без модели пользователя, пользователя нельзя корректно связать с бронью без обновления домена и БД, а тесты авторизации бессмысленны без обновлённого API-пайплайна.

## 2. Какие правила появились у бронирований

До sprint 8 бронь умела только создаваться и обрабатываться в фоне. Теперь действуют дополнительные правила:

- **нельзя бронировать прошедшее событие** — если событие уже началось, бронь не создаётся (`400`);
- **лимит активных броней на пользователя** — не больше `10` одновременно активных (`Pending` или `Confirmed`) броней; при превышении `409`;
- **отмена брони** — бронь переводится в статус `Cancelled`, место возвращается в пул;
- **проверка прав при отмене** — обычный пользователь отменяет только свою бронь, администратор — любую (`403` при нарушении).

## 3. Зачем понадобились пользователи, роли и JWT

Все правила выше требуют ответа на вопрос «кто выполняет операцию». Без идентичности пользователя нельзя:

- записать владельца брони;
- проверить лимит «на пользователя»;
- решить, имеет ли право вызывающий отменить конкретную бронь;
- ограничить управление событиями ролью `Admin`.

Поэтому в систему вводятся:

- перечисление ролей `UserRole` (`User`, `Admin`);
- сущность `User` с логином, **хешем** пароля и ролью;
- JWT-токен как переносчик идентичности и роли между запросами (stateless-аутентификация);
- две роли с разными правами: `Admin` управляет событиями и может отменить любую бронь, `User` бронирует и отменяет только свои брони.

## 4. Почему именно такой порядок работы

План реализации шёл **от ядра к внешним слоям**: сначала домен и контракты, затем security-примитивы, затем persistence, затем use cases, и только потом HTTP-слой и тесты.

Мотивация:

- если начать с контроллеров и JWT, придётся несколько раз переписывать сигнатуры сервисов, как только в них добавится `userId`;
- доменные правила должны жить в Application/Domain, а не в контроллерах, поэтому их фиксируем первыми;
- схема БД должна соответствовать домену раньше, чем появятся auth-сценарии, иначе они «работают в памяти» и ломаются на сохранении.

История коммитов отражает эти этапы: домен → security → persistence → use cases → presentation → tests.

## 5. Что осталось прежним

- Слоистая структура из sprint 7 (Domain / Application / Infrastructure / Presentation) и направление зависимостей.
- Публичные эндпоинты событий и броней; добавились только `POST /api/auth/register` и `POST /api/auth/login`, а к существующим — требование аутентификации.
- PostgreSQL как основная БД, EF Core migrations, Testcontainers для integration-тестов.
- Фоновая обработка `Pending`-броней.
- Формат ошибок `ProblemDetails`.

## 6. Подход к паттернам и принципам

Набор приёмов остался минимальным и оправданным:

- **Factory**: доменные фабрики `User.Create`, `Booking.CreatePending`.
- **Port/Adapter**: `IUserRepository` (порт в Application) и `UserRepository` (адаптер EF Core в Infrastructure); `IPasswordHasher`, `IJwtTokenGenerator` — абстракции security в Application, реализации в Infrastructure.
- **Options**: параметры JWT через `JwtOptions` + `IOptions<>`.
- **Dependency Injection**: composition root остаётся в `Program.cs`.

Не добавлялись Identity framework, refresh-токены, готовые user-stores или сторонние пакеты хеширования — задание требует именно минимальный самостоятельный контур (SHA-256 + JWT), и это сознательно соответствует KISS/YAGNI.
