Задание
В этом спринте вы доработаете сервис бронирования, чтобы он корректно обрабатывал несколько заявок одновременно. 
В предыдущих спринтах вы реализовали базовую логику бронирования и фоновую обработку. Теперь ваша задача — обеспечить потокобезопасность при конкурентных запросах и предотвратить овербукинг.
Вы добавите к событию ограничение на количество мест, защитите критическую секцию «проверка доступных мест + изменение статуса брони» с помощью примитивов синхронизации и обеспечите параллельную обработку заявок в фоновом сервисе.
В результате выполнения проектной работы вы:
реализуете параллельную обработку нескольких заявок на бронирование;
примените примитивы синхронизации (lock, SemaphoreSlim) для защиты критических секций;
обеспечите корректное обновление данных события и брони при конкурентных запросах;
реализуете потокобезопасную логику фоновой обработки бронирований;
предотвратите овербукинг за счёт правильного использования синхронизации.
Требования и функциональность
Проект использует C#, .NET 8 и выше, ASP.NET Core Web API.
Код приложения хранится в том же публичном GitHub-репозитории.
Проект собирается и запускается стандартными средствами (dotnet build, dotnet run).
Тесты запускаются командой dotnet test и успешно проходят.
Swagger доступен и корректно отображает все эндпоинты.

Этап 2. Добавление ограничения мест к событию

Чтобы бронирование имело практический смысл, событие должно знать о доступных местах.
Добавьте в сущность Event два новых поля: 
TotalSeats (int, обязательное) — общее количество мест на событии;
AvailableSeats (int) — текущее количество свободных мест; при создании равно TotalSeats.
Добавьте в Event метод TryReserveSeats(int count = 1): 
возвращает false, если свободных мест недостаточно;
уменьшает AvailableSeats на count и возвращает true, если места есть.
Добавьте в Event метод ReleaseSeats(int count = 1) для освобождения мест (на будущее, при отклонении брони).
Обновите CreateEvent DTO — добавьте поле TotalSeats (int?, обязательное для создания).
Обновите EventInfo DTO — добавьте поля TotalSeats и AvailableSeats.
Убедитесь, что Event.Create(...) теперь принимает totalSeats и валидирует его: значение должно быть больше нуля. При нарушении — ValidationException.
Обновите EventService.CreateEventAsync — передавайте TotalSeats в фабричный метод и возвращайте оба новых поля в EventInfo.
Этап 3. Защита критической секции в BookingService

Конкурентная проблема здесь классическая: два потока одновременно читают AvailableSeats > 0, оба решают создать бронь, и в итоге количество броней превышает количество мест.
Добавьте в BookingService приватное поле блокировки:
private readonly object _bookingLock = new(); 
Оберните всю логику CreateBookingAsync в lock (_bookingLock):
получение события из хранилища;
проверка доступных мест (TryReserveSeats());
сохранение обновлённого события;
создание и сохранение брони.
Это гарантирует, что в любой момент времени только один поток проходит через критическую секцию.
Создайте исключение NoAvailableSeatsException: если TryReserveSeats() вернул false — выбрасывайте это исключение с сообщением "No available seats for this event".
Обновите GlobalExceptionHandler: NoAvailableSeatsException → 409 Conflict.
В BookingEndpoints добавьте документирование нового статуса:
.Produces<ProblemDetails>(StatusCodes.Status409Conflict) 
Важно: lock должен охватывать именно атомарную пару «проверка + изменение». Не нужно блокировать операцию чтения в GetBookingByIdAsync.
Этап 4. Параллельная обработка в BookingBackgroundService

В предыдущем спринте фоновый сервис обрабатывал заявки последовательно. Теперь нужно обрабатывать несколько заявок одновременно, при этом защитив обновление хранилища. 
Также нужно добавить логику отклонения брони — если событие было удалено к моменту обработки или произошла непредвиденная ошибка, бронь должна перейти в статус Rejected, а место — вернуться в пул.  
Замените последовательный foreach на параллельный запуск через Task.WhenAll:
var pendingBookings = _bookingStore.GetPending().ToList();
var tasks = pendingBookings.Select(booking => ProcessBookingAsync(booking, stoppingToken));
await Task.WhenAll(tasks); 
Вынесите логику обработки одной брони в отдельный приватный метод ProcessBookingAsync(Booking booking, CancellationToken stoppingToken).
Добавьте в класс SemaphoreSlim для защиты записи в хранилище:
private readonly SemaphoreSlim _processingSemaphore = new(1, 1); 
В ProcessBookingAsync: 
выполните Task.Delay (имитация внешнего вызова) до захвата семафора — так задержки выполняются параллельно;
захватите семафор (WaitAsync) перед тем, как вызвать booking.Confirm() и _bookingStore.Update(booking);
проверьте, существует ли событие в хранилище; если нет — вызовите booking.Reject(), сохраните бронь и завершите обработку с логом Warning;
если событие найдено — вызовите booking.Confirm() и сохраните бронь;
освободите семафор в блоке finally;
при возникновении неожиданного исключения отклоните бронь через booking.Reject(), верните место через event.ReleaseSeats() и обновите оба хранилища;
корректно обрабатывайте OperationCanceledException и другие исключения.
Добавьте в конструктор BookingBackgroundService зависимость на InMemoryEventStore — она используется при проверке существования события в момент обработки брони.
Почему SemaphoreSlim, а не lock: lock нельзя использовать с await внутри заблокированного блока. SemaphoreSlim — асинхронный аналог Mutex.

Добавьте тесты на смену статуса брони:
Переход в Confirmed:

Переход в Rejected:
После вызова Reject() бронь возвращает статус Rejected и заполненный ProcessedAt.
После Reject()
ReleaseSeats() количество свободных мест восстанавливается.
После Reject()
ReleaseSeats() можно успешно создать новую бронь на то же место.

           AvailableSeats = 0.

Ожидается: 10 броней с уникальными Id.
