# Спринт 4: Параллельная обработка и синхронизация при конкурентных запросах

## Назначение спринта

В sprint 3 была реализована базовая система бронирования с фоновой обработкой. Однако эта система имела критический недостаток: она не была защищена от одновременных конкурентных запросов.

**Главная проблема**: без синхронизации два потока могут одновременно проверить наличие свободных мест, оба увидеть, что место есть, и обе создать бронирование — что приведёт к **овербукингу** (количество броней превысит количество мест).

**Цель sprint 4**: обеспечить:

- **Потокобезопасность при создании бронирования** — защита критической секции "проверка доступных мест + резервирование"
- **Параллельную обработку бронирований** в фоновом worker'е — вместо последовательной обработки
- **Безопасное обновление состояния** при параллельной обработке — использование асинхронных примитивов синхронизации
- **Корректную обработку ошибок** — возврат мест и переход брони в `Rejected` при удалении события или непредвиденной ошибке

## Ключевые изменения

### Модель события

- Добавлены поля `TotalSeats` и `AvailableSeats`
- Добавлены методы `TryReserveSeats(int count = 1)` и `ReleaseSeats(int count = 1)`
- Валидация: `TotalSeats > 0`

### BookingService

- Вся логика `CreateBookingAsync` обёрнута в `lock (_bookingLock)`
- Критическая секция включает: получение события → резервирование мест → сохранение брони
- Выброс нового исключения `NoAvailableSeatsException` при отсутствии мест → `409 Conflict`

### BookingProcessingBackgroundService

- Замена последовательного `foreach` на параллельное `Task.WhenAll`
- Использование `SemaphoreSlim(1,1)` для сериализации записи в store
- Логика обработки вынесена в приватный метод `ProcessBookingAsync`
- Корректная обработка случая удаления события перед обработкой брони — переход в `Rejected`
- Корректная обработка исключений — откат места через `ReleaseSeats`

### Инфраструктура

- Новое исключение `NoAvailableSeatsException`
- Middleware `ExceptionHandlingMiddleware` маппирует его на `409 Conflict`
- Контроллер документирует новый статус в Swagger через `ProducesResponseType`

## Почему это важно

Этот спринт охватывает один из самых важных аспектов многопоточного программирования:

- **Race conditions** (гонки) — когда несинхронизированный доступ приводит к некорректному состоянию
- **Lock-free vs. locked подходы** — почему мы выбираем `lock` и `SemaphoreSlim`
- **Atomicity** (атомарность) — почему критическая секция должна включать ровно нужное количество операций
- **Async/await с примитивами синхронизации** — почему нельзя использовать `lock` с `await`
- **Параллельная обработка** — как безопасно запускать несколько задач одновременно

## Ключевые термины

- **Race condition** — недетерминированное поведение из-за одновременного доступа к общему состоянию
- **Critical section** — блок кода, который должен выполняться только одним потоком за раз
- **Lock** — взаимное исключение на основе объекта (синхронный примитив)
- **SemaphoreSlim** — асинхронный примитив, позволяющий ждать (`WaitAsync`) без блокировки потока
- **Atomicity** — свойство операции быть неделимой (всё или ничего)
- **Overoverbooking** — когда количество броней превышает вместимость события
