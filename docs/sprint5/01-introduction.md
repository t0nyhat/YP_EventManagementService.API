# Спринт 5: PostgreSQL + EF Core

## Назначение спринта

В sprint 4 проект уже умел корректно работать с конкурентными бронированиями, но оставался ограничен in-memory хранением.

Это значит:
- данные исчезают после перезапуска приложения;
- невозможно безопасно масштабировать сервис между процессами;
- тесты и поведение не совпадают с production-моделью хранения.

**Цель sprint 5**: перевести проект на PostgreSQL и Entity Framework Core без потери текущей бизнес-логики (валидация, ограничения мест, фоновая обработка, ProblemDetails).

## Что было сделано

1. Добавлен слой `DataAccess` с `AppDbContext` и Fluent-конфигурациями.
2. Сервисы `EventService` и `BookingService` переведены на работу с `DbSet<T>`.
3. API операций событий приведён к асинхронному контракту.
4. Фоновая обработка переведена на `IServiceScopeFactory`.
5. Регистрация зависимостей обновлена на scoped-модель для работы с `DbContext`.
6. Таблицы БД создаются автоматически при старте через `EnsureCreated`.
7. Тесты адаптированы под InMemory-провайдер EF Core и конкурентный scoped-подход.

## Почему это важно

Sprint 5 закрывает разрыв между учебным API и реальным server-side приложением:

- появляется постоянное хранилище;
- появляется настоящая модель жизненного цикла `DbContext`;
- код начинает учитывать границы scope и потокобезопасность на уровне инфраструктуры;
- тесты проверяют архитектуру, близкую к production.

## Главные учебные выводы

1. `DbContext` — scoped-зависимость, а не singleton.
2. Фоновый singleton-сервис не должен внедрять scoped-сервисы напрямую.
3. Один `SaveChangesAsync()` фиксирует изменения всех отслеживаемых сущностей в контексте.
4. Конкурентные тесты должны имитировать реальные запросы через отдельные scope.
