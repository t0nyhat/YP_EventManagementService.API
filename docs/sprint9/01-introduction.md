# Введение в sprint 9

## 1. Цель спринта

Sprint 9 — самый крупный архитектурный сдвиг проекта: монолит из спринтов 1–8 распиливается на **три независимых микросервиса**, которые общаются между собой **только асинхронно** через Apache Kafka:

1. **Users/Auth** — регистрация, вход, выдача JWT-токена;
2. **Events** — CRUD событий и учёт доступных мест;
3. **Bookings** — создание, подтверждение и отмена броней.

Главное требование задания: когда бронь подтверждается, Bookings публикует в Kafka событие `BookingConfirmed`, а Events, подписанный на топик, уменьшает количество доступных мест. Никаких прямых HTTP/gRPC-вызовов между сервисами нет.

## 2. Зачем делить монолит и по каким границам

В монолите всё держалось на общей схеме БД и прямых вызовах: `BookingService` напрямую читал и изменял `Event`, таблица `bookings` имела FK на `events` и `users`. Это удобно, пока команда и нагрузка малы, но связывает жизненные циклы: нельзя выкатить изменение броней, не задев события.

Границы разреза выбраны по **зонам ответственности** (по сути — по агрегатам домена):

- идентичность и доступ → Users;
- каталог событий и места → Events;
- жизненный цикл брони → Bookings.

Каждый сервис получает **свою базу данных** — это ключевой признак микросервиса. Общая база означала бы скрытую связанность через схему: миграция одного сервиса ломала бы другой.

## 3. Событийная модель и eventual consistency

Раз у сервисов разные базы, привычная транзакция «создать бронь + уменьшить место» невозможна. Вместо неё — **согласованность в конечном счёте** (eventual consistency):

- Bookings при создании брони **не проверяет**, существует ли событие и есть ли места — он отвечает только за брони;
- бронь подтверждается локально, факт подтверждения публикуется как событие `BookingConfirmed`;
- Events обрабатывает событие асинхронно и уменьшает места; если событие не найдено, уже началось или мест нет — фиксирует это в inbox и пропускает сообщение.

Цена такой модели — окно рассогласованности и «крайние случаи» (бронь подтверждена, а места нет). Задание сознательно ограничивает scope: компенсирующее событие (`BookingRejected`/`BookingCancelled`) не требуется, крайние случаи обрабатываются логированием и пропуском. Эти ограничения зафиксированы в корневом [README](../../README.md) в разделе «Осознанные ограничения».

## 4. Какие гарантии всё-таки даются

Несмотря на асинхронность, решение держит два инварианта строго:

- **сообщение не теряется**: статус брони и outbox-строка сохраняются в одной транзакции БД (паттерн **Outbox**), публикация ретраится до успеха; консюмер коммитит offset только после успешной обработки, а при ошибке возвращается к сообщению через `Seek`;
- **сообщение не применяется дважды**: Events ведёт таблицу **Inbox** с первичным ключом по `booking_id` — повторная доставка того же события не уменьшит места второй раз (идемпотентность).

Вместе это даёт семантику **at-least-once delivery + идемпотентный обработчик**, что эквивалентно exactly-once на уровне бизнес-эффекта.

## 5. Что осталось прежним

- Внутри каждого сервиса — та же Clean Architecture из спринта 7: Domain / Application / Infrastructure / Presentation и направление зависимостей внутрь.
- Доменные правила и модель из спринта 8 (статусы брони, лимит активных броней, роли, валидация событий) — перераспределены по сервисам, но не переписаны.
- JWT-контур спринта 8: токен выдаёт Users, claims (`NameIdentifier`, `Name`, `Role`, `sub`, `unique_name`) прежние; Events и Bookings только валидируют токен с общими `Issuer`/`Audience`/`SigningKey`.
- PostgreSQL + EF Core migrations, `ProblemDetails` для ошибок, Swagger с кнопкой `Authorize`, фоновая обработка `Pending`-броней.

## 6. Подход к паттернам и принципам

Новые приёмы спринта — ровно те, что нужны для надёжного асинхронного обмена:

- **Shared Kernel (минимальный)**: проект `EventManagementService.Contracts` — только имя топика, record события и настройки сериализации; никаких ссылок на EF, ASP.NET или Kafka-клиент.
- **Transactional Outbox** (Bookings): подтверждение брони и намерение опубликовать событие — одна транзакция; отдельный фоновый паблишер доводит публикацию до конца.
- **Inbox / Idempotent Consumer** (Events): дедупликация по `booking_id` на уровне первичного ключа БД.
- **Optimistic Concurrency**: статус брони — concurrency token, защищает от гонки «отмена во время подтверждения».
- **Advisory Lock** (PostgreSQL): лимит активных броней пользователя проверяется атомарно и работает при нескольких инстансах сервиса.

Не добавлялись: сервис-дискавери, API-gateway, сага-оркестраторы, schema registry — для учебной задачи это лишнее (KISS/YAGNI), а их отсутствие честно задокументировано как ограничение.
