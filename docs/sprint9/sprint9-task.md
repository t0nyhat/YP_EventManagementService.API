Задание
В предыдущих спринтах вы построили монолитное приложение по управлению мероприятиями: единое решение с доменными правилами, бронированиями, пользователями и JWT-аутентификацией. 
В этом спринте вы выполните декомпозицию монолита на три независимых микросервиса и наладите между ними асинхронный обмен сообщениями через Apache Kafka.
Монолит разделяется на три сервиса, у каждого — своя база данных и зона ответственности:
Users/Auth — регистрация, вход и выдача JWT-токена;
Events — управление событиями (CRUD) и учёт доступных мест;
Bookings — создание и отмена броней.
Главное требование  — наладить взаимодействие сервисов без прямых синхронных вызовов. 
Когда бронь подтверждается, сервис Bookings публикует в Kafka событие BookingConfirmed. Сервис Events подписан на это событие и уменьшает количество доступных мест у соответствующего события. 
Система становится событийно-ориентированной и согласованной в конечном счёте (англ. eventual consistency): Bookings ничего не знает про внутреннее устройство Events и не вызывает его API напрямую.
JWT остаётся общим: токен по-прежнему выдаёт только сервис Users, а Events и Bookings проверяют этот же токен (общие секрет, издатель и аудитория).
В результате выполнения проектной работы вы:
разделите монолит на три самостоятельных сервиса, каждый со своей базой данных и жизненным циклом;
вынесете общий контракт сообщения и имена топиков в отдельный разделяемый проект;
настроите подключение к Apache Kafka и реализуете публикацию события BookingConfirmed в сервисе Bookings;
реализуете подписку на топик в сервисе Events и обработку события — уменьшение доступных мест;
настроите проверку одного и того же JWT-токена в каждом сервисе;
соберёте всю систему (Kafka + Zookeeper + три базы данных + три сервиса) в docker-compose и запустите её одной командой.
Требования и функциональность
Проект использует C#, .NET 8 и выше, ASP.NET Core Web API.
Код приложения хранится в том же публичном GitHub-репозитории.
Решение содержит три отдельных сервиса; у каждого своя база данных PostgreSQL.
Общий контракт события и имена топиков вынесены в отдельный разделяемый проект, который подключают сервис-издатель и сервис-подписчик.
Сервис Bookings при подтверждении брони публикует в Kafka событие BookingConfirmed.
Сервис Events подписан на топик и при получении события уменьшает количество доступных мест у события.
Сервисы не вызывают друг друга напрямую по HTTP — обмен идёт только через Kafka.
JWT-токен выдаёт сервис Users (POST /auth/login); сервисы Events и Bookings проверяют этот же токен.
Управление событиями (POST/PUT/DELETE /events) доступно только роли Admin; эндпоинты броней требуют аутентификации.
Вся система запускается через docker compose up: поднимаются Zookeeper, Kafka, три базы данных и три сервиса.
Swagger доступен у каждого сервиса и корректно отображает его эндпоинты.
Как работать над заданием
Этап 1. Подготовка к работе

Убедитесь, что проектная работа восьмого спринта успешно завершена.
Переключитесь на ветку main вашего репозитория и выполните git pull для синхронизации.
Создайте новую ветку sprint-9 из ветки main и переключитесь на неё.
Всю работу по этому проекту ведите в ветке sprint-9.
Этап 2. Разделение монолита на сервисы

Спланируйте структуру решения: три независимых сервиса и один разделяемый проект с контрактами. Каждый сервис стройте по тем же принципам чистой архитектуры, что и в прошлых спринтах — со слоями Domain, Application, Infrastructure и Presentation.
Выделите сервис пользователей — регистрация, вход, хеширование пароля и генерация JWT-токена.
Выделите сервис событий — управление событиями (CRUD) и учёт доступных мест.
Выделите сервис броней — создание и отмена броней.
Каждый сервис получает свою базу данных и свой контекст БД. Разделите данные по сервисам; навигационные свойства между сущностями разных сервисов уберите — связь остаётся только по идентификаторам пользователя и события.
Для каждого сервиса создайте отдельную миграцию EF Core под его собственную базу.
Принципы чистой архитектуры, EF Core, JWT и доменные правила вам уже знакомы по прошлым спринтам — используйте эти знания, распределив код между сервисами и их слоями. Новое здесь — граница между сервисами: у каждого своя база, и они не делят между собой одну схему.
Этап 3. Разделяемый контракт события

Сервисы общаются сообщениями, и формат сообщения должен быть одинаковым у издателя и подписчика. Чтобы не дублировать описание, вынесите его в отдельный проект-библиотеку, который подключат оба сервиса.
В этом проекте опишите:
имя топика — как константу, чтобы издатель и подписчик ссылались на одну и ту же строку (например, booking-confirmed);
контракт события BookingConfirmed — простой неизменяемый тип с минимально необходимыми данными: идентификаторы брони, события и пользователя, количество мест и момент подтверждения.
Контракт — это публичный «договор» между сервисами. Не кладите в него внутренние детали реализации: только то, что действительно нужно подписчику.
Этап 4. Подключение Kafka — публикация события (Bookings)

Подключите NuGet-пакет клиента Kafka — Confluent.Kafka.
Вынесите адрес брокера в конфигурацию (секция Kafka, ключ BootstrapServers), чтобы локально и в Docker он мог отличаться.
Реализуйте компонент-издатель за интерфейсом: абстракцию определите в слое Application, а реализацию на Kafka — в слое Infrastructure. Внутри он создаёт продюсера, сериализует событие в JSON и отправляет его в топик. 
Учтите два важных момента:
продюсер — тяжёлый потокобезопасный объект; создавайте его один раз (регистрируйте как singleton) и освобождайте при остановке приложения (IDisposable);
задавайте ключ сообщения: сообщения с одинаковым ключом попадают в один раздел (англ. partition) и обрабатываются по порядку. Логично использовать идентификатор события, чтобы все брони по одному событию шли последовательно.
Публикуйте событие в момент подтверждения брони. Фоновый обработчик подтверждения «висящих» броней у вас уже есть с прошлых спринтов. 
Важно: сначала сохраните изменение статуса брони в свою базу и только потом публикуйте событие. Сервис броней отвечает только за брони, он не уменьшает места у события и не обращается к сервису событий напрямую.
Этап 5. Подключение Kafka — подписка на событие (Events)

Теперь реализуйте приём сообщений в сервисе событий.
Подключите тот же пакет Confluent.Kafka. В конфигурацию добавьте адрес брокера и группу потребителей (ConsumerGroup). Группа определяет, как сообщения распределяются между экземплярами сервиса: внутри одной группы каждое сообщение получает только один экземпляр. Для разных сервисов используйте разные группы.
Реализуйте фоновый сервис-подписчик на базе BackgroundService (его место — слой Infrastructure). Он подписывается на топик, в цикле читает сообщения, десериализует BookingConfirmed и уменьшает количество доступных мест у соответствующего события. 
Помните о двух нюансах:
метод чтения у клиента Kafka блокирующий;
BackgroundService — singleton, а репозитории и контекст БД — scoped.
Зарегистрируйте подписчик как BackgroundService, чтобы он запускался вместе с приложением.
Обработайте крайние случаи (событие не найдено, нет свободных мест) явно — пропуском с логированием, чтобы подписчик не падал на одном «плохом» сообщении.
Продумайте создание топика. Один из сервисов должен гарантированно создать топик при старте, иначе при первом запуске подписчик может не найти топик, к которому подписывается.
Удобно сделать это в сервисе-подписчике (Events): при старте через админ-клиент Kafka создайте топик, если его ещё нет, а если он уже существует — просто пропустите. Не валите запуск сервиса, если топик создать не удалось: оформите это отдельным компонентом (например, hosted-сервисом), который отрабатывает до запуска подписчика.
Этап 6. Проверка JWT в каждом сервисе

Аутентификация вам знакома, поэтому коротко обозначим: токен выдаёт только сервис Users. Сервисы Events и Bookings этот токен проверяют.
Используйте общие значения секрета, издателя и аудитории во всех трёх сервисах — иначе токен, выданный одним сервисом, не пройдёт проверку в другом. Вынесите их в конфигурацию.
В сервисах Events и Bookings подключите JWT-аутентификацию и авторизацию в пайплайн.
Сохраните прежнее разграничение прав: управление событиями (POST/PUT/DELETE /events) — только для роли Admin через атрибут [Authorize(Roles = "Admin")]; эндпоинты броней требуют аутентификации, идентификатор пользователя читайте из claims.
Этап 7. Запуск системы в Docker

Запустите все необходимые компоненты для работы системы в Docker. 
Мы подготовили пример того, как может выглядеть docker-compose инфраструктуры (базы данных, Kafka). Вы можете воспользоваться этим файлом для поднятия инфраструктуры или самостоятельно дополнить его для запуска всей инфраструктуры и сервисов вместе.
Этап 8. Проверка и оформление

После успешного запуска проверьте сценарий целиком: 
зарегистрируйте пользователя и получите токен в сервисе Users;
создайте событие администратором в сервисе Events, запомните количество мест;
создайте бронь в сервисе Bookings и дождитесь её подтверждения;
убедитесь, что в сервисе Events количество доступных мест уменьшилось — это значит, что событие прошло через Kafka.
Убедитесь, что сервисы не вызывают друг друга напрямую: уменьшение мест происходит только через обработку события из Kafka.
Обновите README.md: 
опишите состав системы (три сервиса, их базы и порты);
опишите поток данных BookingConfirmed: кто публикует, кто подписан, что происходит при получении;
добавьте инструкцию по запуску.
Сделайте финальный коммит и пуш всех изменений в ветку sprint-9 на GitHub.

У каждого сервиса своя база данных и своя миграция EF Core.

Хорошие практики (необязательно для зачёта):

Продюсер Kafka зарегистрирован как singleton и корректно освобождается (IDisposable).
В подписчике на каждое сообщение создаётся отдельный scope для scoped-зависимостей.
Адрес Kafka и строки подключения вынесены в конфигурацию и переопределяются переменными окружения в Docker.
В качестве ключа сообщения используется осмысленное значение (EventId), обеспечивающее порядок обработки.
Один из сервисов создаёт топик при старте, чтобы система работала «из коробки» даже на пустом брокере.
Отлично (всё выполнено на высоком уровне):

Событие сначала сохраняется в базу и только потом публикуется, соблюдён корректный порядок при согласованности в конечном счёте.
Обработка повторных или дублирующихся сообщений не приводит к некорректному уменьшению мест (идемпотентность).
Для каждого сервиса написан свой Dockerfile с многоступенчатой сборкой.
Swagger каждого сервиса настроен для работы с JWT (кнопка «Authorize»).
